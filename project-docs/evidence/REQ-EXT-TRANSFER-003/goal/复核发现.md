## 1. G1 — 上传期间 `upload_session.confirmed_offset` 恒为 0（主人上报「额外1」）

**现象（实测）**：客户端已发 512 KiB / 1 MiB / 1.5 MiB 三个采样点，该行始终
`session_id=3438  status=uploading  confirmed_offset=0  expected_size=2097152`。
上传**正常完成**后仍为 0（行 3436/3437/3438 三条 `done` 行，`confirmed_offset` 全 0）。

**根因（代码锚点）**：写该列的唯一入口是 `OperateDB::updateUploadOffset()`
（`Server/operatedb.cpp:493-503`，`UPDATE ... WHERE session_id=? AND status='uploading'`），
其**唯一调用点**在 `MsgHandler::abortUpload()`（`Server/msghandler.cpp:1337-1340`）——
即只有暂停/取消/空闲回收这类"中止"路径才落库。正常完成走
`finishUploadSession(sessionId,"done",fileId)`（`Server/msghandler.cpp:1718`；
`Server/operatedb.cpp:505-523` 只写 `status`/`file_id`），偏移量不写、也不置为文件大小。

**影响**：`upload_session` 里唯一能表示"服务端收到多少"的字段在**成功上传**上永远是 0，
只有被中止过（且恰好被 107 停过）的会话才有真值；同一列在"新上传"（0）与"续传会话"
（= 暂存大小）之间取值口径不一致。管理侧/测试侧按该列判断进度只能得到错误结论。

**定性更正（2026-10-08 主人质询"偏移量不是写文件一块落库一次吗"后复核）：这是设计承诺未实现，不是"设计如此"。**

- **承诺**：REQ-EXT-FILE-001 T4 任务记录原文——"上传会话落库：`uploadfileinit/UPLOADFILE_DATA/完成`
  **三阶段**把 offset/过期/临时路径持久化 `upload_session`"（`project-docs/tasks/REQ-EXT-FILE-001/task.md:33`）；
  需求文档同列该字段（`requirements/REQ-EXT-FILE-001.md:18`"已确认 offset"）。
- **实现**：`updateUploadOffset` 自 `6e023d5`（T4 groundwork，提交自述"均未被 handler 调用"）定义起**无调用者**，
  `c452eb3`（FILE-002）时仍是死代码；**第一次被调用是 `35dfce7`**（TRANSFER-001 AUD-4 竞态修复），
  且唯一调用点在 `abortUpload()`。即 **DATA 阶段从未落库**。开发节点2 的写侧切换计划
  （同文件"剩余开发"第 1 条）只列了 INIT 与完成两处 —— DATA 阶段在**计划层面**就已丢失，
  而当时没有任何断言覆盖"上传过程中 offset 前进"（T-20 只断言 107 之后 == 暂存大小），测试与审计因此都没抓到。
- **完成阶段也不符后续设计**：REQ-EXT-FILE-002 design §2.4 要求完成行落
  `status='done'`、`file_id`、**`confirmed_offset=size`**、`staging_path=''`；
  该写法只在**秒传命中**路径实现（`insertCompletedUploadSession`，`Server/operatedb.cpp:465-491`），
  真实上传路径走 `finishUploadSession`（`Server/operatedb.cpp:505-523`），offset 与 staging_path 都不写。
- **影响面收窄（但不为零）**：该列**今天没有任何产品逻辑读取**——`UploadSessionLookup.confirmedOffset`
  （`Server/operatedb.h:188`）被填充却无消费者；97 的 `status='uploading'` 幂等短路
  （`Server/msghandler.cpp:1534-1549`）是**从暂存物理大小重推** offset 而非读该列。
  故不是功能缺陷，而是 **T4 承诺未兑现 + 记录失真**（我上一轮"仅可观测性"的定性偏轻，以本节为准）。

## 2. G2 — 暂停后断点续传会新建一条上传会话（主人上报「额外2」）

**现象（实测）**：发 1 MiB 后发 107（暂停）→ 行 `3439 expired confirmed_offset=1048576`；
随后以新 id 发 29（续传，服务端回带 `resumeOffset=1048576`）→ **新增**行
`3440 uploading confirmed_offset=1048576`。**行数 1 → 2**，续传完成后 `3439 expired` 残留、
`3440 done`。即：一次逻辑上传 = 每次暂停/续传各留一行。

**根因（代码锚点）**：三条建会话路径都是无条件 INSERT：
- 个人 29：`Server/msghandler.cpp:1238-1245`（仅当采纳本连接前序 97 的暂存才不插）
- 个人 97：`Server/msghandler.cpp:1497-1510`（仅当**同一 `client_request_id`** 有历史行才原地重置）
- 群 101：`Server/msghandler.cpp:2386-2388`

而暂停/取消把旧行置 `expired`（`Server/msghandler.cpp:1339`）。续传按 DESIGN §2.3-S3 走
"新 id 重走 29"，此时 (a) 29 不携带 `client_request_id`，(b) 内存里的 `m_pendingFastcheck` 已失效，
→ 命中 `createUploadSession` 新插一行。原地复用的既有设施 `restartUploadSession()`
（`Server/operatedb.cpp:435-461`，"绝不再插一行"）**只被 97 的请求键路径使用**。

**影响**：`upload_session` 行数随暂停/续传次数线性增长；同一文件的历史真值分散在
`expired` 行里（G1 的偏移量恰好在这些行上才有值），完成行反而是 0——两处叠加后该表
无法回答"这个文件上传到哪了、传过几次"。

## 3. G3 — 上传吞吐 ~0.2–0.3 MiB/s：瓶颈是**服务端每块重开写句柄**（≈13 ms/块），不是块大小、不是线程、不是句柄销毁成本（主人上报「额外3」）

**实测（`probe_upload_review.log`）**：8 MiB 文件

| 客户端块大小 | 用时 | 吞吐 |
|---|---|---|
| 4096 B（现状） | 28.58 s | **0.28 MiB/s** |
| 16308 B（协议上限内最大值） | 7.32 s | 1.09 MiB/s |

**归因（`probe_upload_cost.log` + `probe_file_pattern.log` + `probe_open_cost.log` + `probe_qfile_cost.log`）**：

| 观测 | 数值 |
|---|---|
| 心跳 50/51 往返（纯网络+事件循环） | 0.57–1.07 ms（首轮）/ 3.5–23 ms（复跑，机器繁忙） |
| 上传每块端到端（1024 / 4096 / 16308 B） | 20.7 / 18.9 / 18.5 ms —— **与块大小几乎无关** |
| 微基准：256 块 × 4096 B，**每块 open+write+close** | **30.2 / 34.2 ms 每块** |
| 微基准：同量数据，**单句柄 seek+write** | **0.35 ms 每块**（flush 0.38 ms） |

**三段分离（raw Win32 ctypes，`probe_open_cost.py`；无任何线程参与）**：

| 形态（256 × 4096 B） | 总/块 | CreateFileW | write | CloseHandle |
|---|---|---|---|---|
| 每块 open(RW)+write+close | 14.13 ms | **13.51** | 0.29 | 0.32 |
| 每块 open(RW)+write+fsync+close | 19.14 ms | **13.62** | 4.91 | 0.61 |
| 每块 open(RW)+close（**不写**） | 0.64 ms | 0.48 | — | 0.16 |
| 每块 open(只读)+close | 1.25 ms | 0.70 | — | 0.55 |
| 单句柄 seek+write | 0.13 ms | 0.06 | 0.07 | 0 |
| 顺序写 32 MiB | — | — | — | **112–409 MiB/s（卷健康）** |

**Qt 原生复核（`probe_qfile_cost.cpp`，与服务端同一 API 面，排除 Python 假象）**：

| 形态 | 总/块 | open | write(+flush) | close |
|---|---|---|---|---|
| A 每块 `QFile::open(RW)+seek+write+flush+close`（**服务端现状**） | 12.8 ms | **12.31** | 0.21 | 0.22 |
| B 同上去掉 flush | 12.3 ms | 11.71 | 0.01 | 0.60 |
| C1 单句柄 + 每块 seek+write | **0.2 ms** | 0.05 | 0.08 | 0.05 |
| C2 单句柄 + 每块 seek+write+**flush** | **0.1 ms** | 0.04 | 0.06 | 0.00 |

**结论（修正此前表述）**：
- **不是线程**：`Server/mytcpsocket.cpp:366` 用的是 `QThreadPool::globalInstance()` —— Qt **全局线程池**，
  worker 线程常驻复用；`UploadWriteTask` 是 QRunnable，每块只新建一个小任务对象，**不新建线程**
  （回调用 `QMetaObject::invokeMethod(..., QueuedConnection)` 投回服务端线程）。三支探针
  （Python io / raw Win32 / Qt QFile）**都不含任何线程**，同样复现 12–14 ms/块。
- **不是"句柄创建/销毁"本身**：CloseHandle 仅 0.32 ms；对**未被写过的**文件 open+close 只要 0.48–0.64 ms；
  单句柄基线 0.13 ms。
- **真正的成本项 = "对一个刚被写过的文件再次以写权限打开"（每块重开写句柄）**，12.3–13.5 ms 全部落在
  `CreateFileW` 里，且**显式 fsync 不能把它移走**（open+write+fsync+close 仍 13.62 ms）。机制上属
  文件系统/过滤驱动在"写打开一个刚被修改的文件"时做的收敛（本机 E: 卷 + 常驻过滤驱动；具体归属未再深挖，
  对本需求不影响决策）。**卷本身健康**（顺序写 112–409 MiB/s）。
- **修复方向因此更硬**：单句柄形态 0.1–0.2 ms/块，比现状快 **~64–128×**；且 C2 显示**保留每块 `flush()`**
  仍然是 0.1 ms/块（Qt 的 `flush()` 在本形态下不是 fsync 级开销）→ 修复不需要动 flush 语义。
- **块大小的收益是线性的、且被这 ~13 ms 封顶**：4 KB→16 KB 只快 4 倍，仍只有 ~1 MiB/s。

**影响**：主人 GUI 实测的"4K 太慢"是这条路径的必然结果（本机 400 MB 文件 ≈ 24 分钟）。

## 4. G4 — 客户端分片 4096 B 硬编码 + 单块在途

`Client/uploader.cpp:71` `m_file.read(4096)`；`Uploader` 每发一块等一个 32 ACK
（`Client/uploader.cpp:43-87`，`m_waitingAck`）。服务端 `Server/mytcpsocket.cpp:356-367`
以 `cp->writeInFlight` 单块在途为闸（重叠发送会被判 `ok=false` 直接失败）。
→ 吞吐 = 块大小 / (RTT + 每块服务端成本)。块大小是唯一可调的杠杆（本需求不改单块在途模型）。

## 5. G5 — 分片大小被服务端入站上限封死（代码事实）

`Server/protocol.h:197-198`：`MAX_INBOUND_PDU_SIZE = 16*1024`、`MAX_PENDING_INBOUND_BYTES = 256*1024`
（`frozen_paths`）；`Server/mytcpsocket.cpp:639-659` 按前者拒绝、按后者断开。
`sizeof(PDU) = 76` → 单块正文上限 **16308 B**。
→ 要让分片"更大"（主人要求），**必须改冻结面常量**，属契约变更（LARGE + 主人批准）。
安全面：两常量是既有抗 DoS 上界（SEC-001 面），上调后仍须保持"每连接有界"，design 节点裁定终值。

## 6. G6 — 客户端上传暂停/续传不摘旧 id 映射（防御不对称）

下载侧 `pause()/resumeDownload()` 明确摘除旧 id 映射（`Client/transfertask.cpp:934`、`972`，
TRANSFER-002 §4.3"必做防御"），上传侧 `pause()`（`Client/transfertask.cpp:955-966`）与
`resume()`（`Client/transfertask.cpp:1000-1019`）**没有**对应动作：`resume()` 只插新映射不摘旧映射，
旧 id 仍指向同一任务。`onUploadDataRespond`（`Client/transfertask.cpp:674-691`）凭 id 找到任务后
直接把 (ret,nextOffset,complete) 喂给**当前** uploader，不校验响应 id 与 uploader 自身 id 一致。
窗口极窄（服务端 ACK 先于 108 发出，客户端同事件循环处理），后果是任务被误判失败而非静默损坏。
→ 与下载侧对齐收口，成本约 2 行。

## 7. G7 — 断线后传输任务永久停留在"传输中"（**范围外，复核发现**）

`Client/client.cpp:565-573` `onSocketDisconnected()` 只弹重连窗；心跳超时
（`Client/client.cpp:169-173`）只调 `onServerLost()`。`TransferManager` 全无连接感知
（`grep isConnected|socketState|disconnect|lost Client/transfertask.cpp` = 0 命中）。
→ 服务端中途消失时，在途上传/下载既收不到 32/43 也无人置失败，**任务行永远"传输中"且占着名额**，
队列不再前进；重连登录后 `setCurrentUser()` 对同一用户提前返回（内存为准），任务不复位。
这正是 REQ-EXT-TRANSFER-001 验收 9「断线后任务标记失败可重试」与 design §6.3 第 9 项人工条目
所要覆盖的行为，该条目在 2026-10-01 的独立测试报告中记为 **NEEDS-HUMAN、未执行、不计 pass**
（`evidence/REQ-EXT-TRANSFER-001/independent-test/test-report.md:97-103`）——即**未验证**，
本轮代码复核结论为**未实现**。建议另立修复任务（客户端生命周期，不属本需求）。

## 8. G8 — 暂存键不含群作用域：群上传与个人根上传可共用同一暂存文件（**范围外，复核发现**）

`ResumableUploadSession::beginStaged` 的键 = `sha1(owner | parentPath | displayName | totalSize)`
（`Server/resumableuploadsession.cpp:84-93`）。群上传固定传 `parent="/"`
（`Server/msghandler.cpp:2377-2379`），而个人上传到**用户根**时 `normalizeParent` 也返回 `"/"`
（`Server/fileobjectstore.cpp`，"rest 为空 → `/`"）。
→ 同一 owner 下，**群上传** 与 **个人根目录上传** 的同名同大小文件落到同一个 `.part`；
两个不同群的同名同大小文件同样共用。并发时互为破坏（写偏移互相错位/内容混合），
串行时后者会以"续传"姿态接在前者的暂存上（内容不同则 finalize SHA 复算失败，数据不落定）。
建议另立任务（改键 = 改变既有暂存归属，需单独立项与迁移处置）。

## 10. 取证口径与局限（诚实标注）

- 探针为 Python 同步驱动（每块等一个 ACK），其自身开销 ~0.1–0.2 ms/块，**不构成** 18–30 ms 的量级；
  产品客户端为 C++ 事件驱动，块间开销更低，故实测吞吐是**下界**，缺陷方向不受影响。
- `probe_file_pattern` 的 open/close 成本（30 ms/块）是本机（E: 卷 + 杀软过滤驱动）的实测值，
  **具体毫秒数不可移植**；可移植的是"每块一次 open+close 相对单句柄 ~100×"的**结构结论**。
- 本节点不修改产品源码、不改验收标准；G7/G8 属复核产出，是否纳入修复范围由主人定。
