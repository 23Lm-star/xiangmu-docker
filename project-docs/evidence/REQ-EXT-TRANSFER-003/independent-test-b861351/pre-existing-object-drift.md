# 既有数据漂移：主人历史文件的实体对象不在当前运行树（FACT，非本轮引入）

发现：2026-10-08 22:4x，主人 GUI 一轮后复核 `wcy` 的对象实体时发现。

## 事实

- `wcy` 共 17 个独立对象；**在 `dist/filesys` 里有实体且大小一致的只有 4 个**：
  `781`(0 B 空内容去重)、`811`(9 B)、`812`(1.6 MB)、`1000421`(173 MB，今晚新传)。
- **13 个对象实体缺失**：`82`(19 B)、`83`(18 B)、`98`(10.6 MB)、`99`(3.7 MB)、`101`(2.9 MB)、
  `102`、`103`(171 MB)、`104`、`105`、`106`、`107`、`108`、`109`。
  其中仅 `82/83` 在旧运行树 `Server/filesys/objects/` 里找到了实体；其余在三棵现存树
  （`dist/`、`Server/filesys/`、`build/wt-claude/dist/`）中均不存在。
- DB 的 `user_file` 行仍是 `active` → 客户端列表会显示这些文件，但**下载必然失败**。
  这正是主人报的"转正的文件元对象在存储路径找不到"——对象是**旧文件**，与今晚新传无关。

## 归因（不是本轮、也不是 003 引入）

- 与本轮无关的证据：本轮独立测试节点的清理只删"非测试用户零引用"的对象；`98/99/101/781`
  在干跑阶段被明确列为"保留"，`103` 因被 `wcy` 引用而不在孤儿集合内（干跑报"实体合计实盘 4.0 MiB"，
  不可能包含 171 MB 的 103）。删后复核悬空引用 = 0。
- 与本轮无关的第二条证据：`build/wt-claude` 与已删除的 `build/wt-indtest`（其副本）里都没有这些实体。
- 更可能的历史原因（claim，未复测）：运行树在 2026-10-01（`0d92607`）从"源码树 cwd=Server +
  filesPath=./filesys"改为"cwd=dist + ./filesys"；此后的回收/TTL 或历史清理删掉了这些对象的实体，
  但共享 `mydb` 里的行与引用未同步。共享库跨多棵工作树复用会放大这类漂移。

## 影响与处置建议

- 对新需求（TRANSFER-003）**无影响**：本需求的上传/下载路径用新对象，实体写入当前运行树。
- 若要止住观感混乱：把 `wcy` 这 13 个"有行无实体"的条目及其 object 行清掉（另一条命令，需主人执行或授权）；
  或重建这些文件后重新上传以刷新实体。
- 未做任何处置（属主人数据）。
