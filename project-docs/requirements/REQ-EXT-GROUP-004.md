# REQ-EXT-GROUP-004 已读游标：连续前缀语义

## 1. 分支信息

- 分支：`feat/req-ext-group-004-read-cursor`
- 层级：**MEDIUM**（改生产源码、有验收标准；**不触碰 frozen_paths**，协议头零改动）
- 依赖：`REQ-EXT-GROUP-002`（可靠群文本消息，已合并）；本需求只改客户端已读语义与状态归属，服务端**零源码改动**

## 2. 目标

修掉"已读游标报最大收到"造成的未读失真与消息永久丢失，并让未读数在拉取补齐后立即收敛。

用户可见目标：**未读数不再说谎**——群里出现投递空洞时不下假降，补齐后立即收敛到真值。

## 3. 根因（改前事实）

实时投递是尽力而为的：服务端每连接出站队列满即丢弃该连接的实时事件
（`Server/mytcpsocket.cpp:517-536`，注释即写明"由游标拉取兜底"）。
因此"收到的最大 seq"与"已连续读到的 seq"不是一回事。

- 客户端却把 `m_lastSeq`（**已渲染最大 seq**，`Client/groupchat.cpp:106-112`）当作已读锚点上报（`Client/groupchat.cpp:98-104`）。
- 复现：窗口开着，群内 1–100 条，客户端只实时收到 1–10 与 90，11–89 被队列丢弃 → 客户端渲染 90 → 上报 90 → 服务端钳到 90 → **11–89 被永久判为已读**，未读从 90 掉到 10，且再也不会回到未读区间。
- 客户端无乱序缓冲、无前缀推进函数、窗口打开期间无任何补洞拉取（拉取只在首次打开窗口触发一次，`Client/groupchat.cpp:214-218`）。
- 状态归属错位：未读状态有两套（`Group::m_unreadByGroup` 与 `GroupChat::m_unread/m_groupLastSeq`），且首次登录后为空——只有打开过群聊窗口的群才有状态。

服务端侧**已经是正确语义**，本需求只把它钉住，不改：
- 已读确认单调钳制 `LEAST(GREATEST(last_read_seq,?), 群水位)`：不回退、不越界、不拒绝（`Server/operatedb.cpp:1812-1815`）。
- 未读数由服务端计算 `COUNT(seq > last_read_seq AND seq <= last_seq)`（`Server/operatedb.cpp:1620-1625`、`1782-1787`）。

## 4. 设计

### 4.1 语义

已读锚点 = **已连续拿到的最长前缀的末尾**，绝不是收到的最大 seq。
实时与拉取**走同一个推进入口**（`onMessageArrived`），保证两条来源路径不会各自维护游标。

```
A. seq == 游标+1        → 前缀延长；顺带循环消费乱序缓冲区（可能一次跳多格）→ 上报
B. seq >  游标+1        → 有洞：消息照渲染，游标绝不推进；触发前向拉取补洞
C. seq <= 游标          → 重复/迟到：丢弃，不影响游标
```

### 4.2 状态归属：会话级，登录即就位

群读状态属于**账号会话**，不属于某个窗口。`GroupChatState` 由 `Client` 持有（`group_id → state`），
登录成功时清空重建并取一次锚点，窗口只是读写者——窗口开关不影响语义。

- 首次取锚点时机：登录响应 `ret==1` → 主界面显示后 → **事件循环下一轮**（与既有 `flushfriend()` 同一处，`Client/msghandler.cpp:90`），发一次 95，96 一次性落地全部群的
  `last_seq`（水位）与 `last_read_seq`（游标）。
  - 不能更早：actor 未建立，95 必被拒（`Server/operatedb.cpp:1611`）。
  - 不能更晚：现状是"第一次打开窗口才取"（`Client/groupchat.cpp:60-66`），未打开过的群启动时状态为空。
- 断线重连走**强制重新登录**（`Client/client.cpp:386,394-404`），`ret==1` 是全客户端唯一的会话建立路径，
  因此同一钩子天然完成重锚；`forceReLogin()` 时必须清空旧会话状态，避免跨账号串号。

### 4.3 两个数各自的推进规则（要害）

| 字段 | 含义 | 能否本地推进 |
|---|---|---|
| 水位 `waterSeq` | 群 `last_seq`："我知道群里最新到哪" | **能**。收到任意 seq 即是水位证据，`max(水位, seq)` |
| 游标 `readCursor` | 连续前缀末尾："我读到哪"（上报锚点） | **不能**。仅在**窗口可见 且 前缀推进（A 分支）**时推进；不可见只更新水位 |

窗口不可见时渲染照常（既有行为），但游标不动——没看到的不能算已读。

### 4.4 上报时机

1. 前缀推进（A 分支）→ 上报，**节流合并**（单次定时器 debounce，窗口尾部取最新游标；合并后仍是前缀末尾，语义不变）。
2. 补洞批次结束（92 mode=0 拉完或 hasMore 耗尽）→ **立即上报**，不节流。
3. 窗口隐藏/关闭 → 立即落地最后一次推进。
4. 洞存在（B 分支）／上翻历史（mode=1）／游标未前进／窗口不可见 → 不上报。
5. 应用退出不做额外落地：暴露面仅节流窗口（≤400ms）内的推进，失败方向是"少标已读"（保守），永不"多标已读"。

### 4.5 未读数显示口径

- 窗口内状态行 = `水位 - 游标`（本地推导）。
- 群列表徽标 = 96 服务端回带值（权威，不变）。
- 两者等价的依据是**序号稠密**：每条消息（含系统消息）都从同一 `group_info.last_seq` 计数器取号并在同事务落一行
  （`Server/operatedb.cpp:1697-1717`、`1272-1290`），故 `COUNT(seq in (a,b]) == b - a`。该等价由 S4 断言钉住。
- 客户端不向服务端自报未读数；服务端只认"已读游标"这一个入参。

## 5. 验收标准

1. 群内 1–100 条、客户端只实时收到 1–10 与 90：界面能看到 90，但**已读只到 10**；未读仍为 90（11–89 没被吞）。
2. 拉取补齐 11–89 后：已读自动推进到 90，未读收敛为 10（91–100），无需重开窗口。
3. 乱序（90 先到、11–89 后到）游标不动；接上后自动推进；重复/迟到不推进、不回退。
4. 已读只增不减；异常大的上报值被服务端夹到群水位（不报错）；迟到的旧值被夹回当前游标（不回退）。
5. 未读数由服务端计算，且与服务端口径 `last_seq - last_read_seq` 一致——洞存在时与补齐后都成立。
6. 上翻历史（mode=1）不影响已读；窗口不可见期间到达的消息不被标记已读。
7. 同一账号换会话（重新登录）后状态重建，不继承上一会话游标。
