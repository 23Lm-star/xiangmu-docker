# REQ-EXT-TRANSFER-001 多文件并行传输（有限并发）

> 阶段：goal（需求分析 + 方案裁决）｜日期：2026-10-01｜分级：**LARGE**
> 事实源：`architecture.md` §4/§10、`interfaces.md` §1/§9、`融合式扩展功能路线图.md`（P1「多文件有限并发」）、`REQ-EXT-ANALYSIS-001.md` §4.2（并行上传另立后续需求）
> 逐字节协议设计、状态机与测试矩阵在 design 节点冻结（`tasks/REQ-EXT-TRANSFER-001/design.md`）。
> **批准前禁止编辑 `Client/protocol.h` / `Server/protocol.h`**（frozen_paths）。

## 1. 需求

在个人文件上传/下载与群文件上传/下载中实现多文件并行传输（有限并发），让多个文件同时进行；用户 2026-10-01 决策追加：每个上传任务可手动**暂停/恢复**与**取消**。

## 2. 范围（用户已确认 2026-10-01）

| 项 | 决策 |
|---|---|
| 传输路径 | **全路径并行**：个人上传、个人下载、群上传、群下载（下载数据通道 42/43 在个人与群间本就共用，统一加编号优于分路径特判） |
| 并发上限 | 单连接默认 **3**（常量，可调）；超限文件自动排队，不报错不丢文件 |
| 客户端 UI | 多选选择器 + 文件级任务列表（进度/状态/失败原因）+ 每个**上传**任务的暂停/恢复/取消按钮 |
| 暂停语义 | 停发并释放并发槽；**恢复走既有断点续传路径**（个人 29/30 `resumeOffset`、群 101/102 `nextOffset` 均已具备——goal 取证核实），从服务端已接收偏移继续，不重传 |
| 取消语义 | 本地移除任务 + 通知服务端释放槽位；staging 不转正、不产生文件条目 |
| 非目标 | 单文件乱序并行分片、动态分片大小、传输任务持久化、跨连接并行、限速/配额、下载任务的暂停/取消（下载仅多选并行） |

## 4. 方案裁决：采用协议级多路复用（方案 B），带 6 处修正

**结论：方向正确，可采用**；是唯一不破坏会话模型的真并行路径。AI 原方案有 2 处硬缺陷、4 处必备补充：

| # | 修正 | 性质 |
|---|---|---|
| M1 | **transfer_id 覆盖初始化握手**：29/30、40/41、101/102、105/106 都要带/回带 id（原方案只写 31/32、42/43）；否则并发初始化时 30/41/102/106 响应无法归属 | 硬缺陷 |
| M2 | **0 值保留 = 旧协议单流路径**（客户端从 1 起发 id）→ 旧客户端与全部既有 e2e 脚本零改动通过，免费回归护栏 | 关键设计 |
| M3 | 服务端 per-transfer 写盘在途位（现单 bool）+ 每连接并发上限 + 超限排队语义 | 必须 |
| M4 | 下载公平调度给出明确算法（每流每轮 1 块 round-robin + 复用出站高水位），否则大文件饿死小文件 | 必须 |
| M5 | 客户端 SHA-256 摘要计算现为 UI 线程同步循环读（Client/file.cpp:419），多选大文件会连续卡死界面 → 移入后台线程 | 新需求下放大 |
| M6 | UI 必须做文件级任务列表（逐文件 QMessageBox 并发时互相打架） | 必须 |

**排除的替代方案**：
- 多连接并行（每文件一条 TCP）：与 REQ-EXT-SESSION-001 单登录版本模型直接冲突（同用户第二次登录踢掉第一条连接），排除。
- 纯客户端队列（不换 id 的串行队列）：总耗时=串行和，只改善「一次选多个」的体验，不产生并行，不采用。

## 5. 设计约束（design / development 必须满足）

- **P1 transfer_id**：u64，客户端生成（Client 级单调计数器，从 1 起），连接内作用域；`0` 保留=旧协议单流路径。
- **P2 覆盖握手**：29/30、31/32、40/41、42/43、101/102、105/106 全部携带/回带；97/98 不加（客户端预检查保持单飞，元数据快往返不占传输时间）。
- **P3 服务端状态表**：每连接 `QHash<id, UploadCtx>`（含 ResumableUploadSession、sessionId、expectedSha、群作用域、单块在途位、kind）+ `QHash<id, DownloadStream>`；替换单 `m_uploadSession`/单下载流；每 transfer 保持「单块在途 + 顺序 offset」模型（不引入乱序分片）。
- **P4 上限**：服务端硬兜底拒绝（防第三方客户端）+ 客户端本地排队；上限常量 3。
- **P5 下载公平调度**：连接级 round-robin（每轮每活跃流 1 块），与 256KB 出站高水位联动；心跳/控制消息不被饿死。
- **P6 暂停/取消（上传）**：暂停=停发+释放槽；恢复=重新 INIT 走既有续传路径（个人 29/30、群 101/102）；取消/暂停释放槽位建议新增轻量 `UPLOADFILE_ABORT`(建议编号 107/108，设计节点裁定形态) + 服务端空闲回收兜底（掉线/崩溃）；取消不删除 staging（沿用既有会话过期语义）。
- **P7 安全**：未知 transfer_id 拒绝且**不回退**；群成员资格仍在 101 判定；数据阶段仅认本连接已登记 id；42/43 客户端发入仍忽略（现状 default）。
- **P8 兼容**：无数据库 schema 变更、无迁移；协议常量两端同值、只追加；旧编号与旧语义零改动。

## 6. 验收标准（业务语言）

1. 个人/群文件窗口可一次多选，多个文件同时进行（默认 3），互不阻塞；单文件失败不影响其他文件，可单独重试。
2. 个人上传与群上传可同时进行（跨窗口）。
3. 并发下载各自独立落盘（同名 (N) 递推互不干扰）、独立完成提示。
4. 传输并发期间心跳/聊天不被饿死（PONG 延迟可接受）。
5. 超过上限的文件自动排队，不报错、不丢文件。
6. 大文件与小文件混合时小文件先完成（公平性）。
7. 每个上传任务可暂停/恢复：恢复从服务端已接收偏移继续（e2e 断言增量字节，不重传）。
8. 每个上传任务可取消：槽位释放、staging 不转正、列表无新条目。
9. 暂停/取消不影响其他并发任务；断线后任务标记失败可重试（续传）。
10. **既有单文件流程与全部既有自动化回归（e2e harnesses）行为逐字节不变。**

## 8. 开放问题（design 节点裁定）

1. `UPLOADFILE_ABORT` 的形态：107/108 请求-响应对 vs 仅请求；与空闲回收阈值、会话状态迁移（uploading→expired/failed）、`restartUploadSession` 的衔接。
2. transfer_id 各 PDU 落位（草案：上传族 [48..55]；40 [48..55]；41 [24..31]（[32..63] 被文件名占）；群族 caData [48..55]——放 caData 而非群信封，避免破坏「尾随字节即拒」的旧脚本重放）。
3. 客户端上传块大小（现 4KB）与并发上限的吞吐关系：本期不调（避免额外变量），design 记录理由。
4. 空闲回收阈值（建议 30–60s）与 `MyTcpServer` 清扫定时器复用方式。

## 9. 风险

| 风险 | 缓解 |
|---|---|
| 双 protocol.h 人工同步漂移 | 常量两端同值、design 逐字节表、审计核对 diff 与批准稿一致 |
| 32/42/43 路由错乱 | id=0 旧路径隔离 + 未知 id 拒绝不回退 |
| 下载调度引入心跳延迟 | round-robin 小块 + 高水位；e2e 断言 PONG 延迟 |
| 4KB 块×3 路并发吞吐提升有限 | 预期收益是多文件同时推进+小文件先完成；动态分片留 P5 后续需求 |
| UI 大改引入回归 | 任务列表独立组件 + NEEDS-HUMAN 人工清单 |
| 暂停恢复路径与既有续传机制语义漂移 | e2e 专项：暂停→恢复→字节增量断言；群/个人两路径各测 |
