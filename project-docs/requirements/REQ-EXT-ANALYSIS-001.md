# 扩展功能需求分析报告

## 1. 文档边界

本报告分析用户提供的 `扩展功能文档.md`。附件是需求输入，不是对代理的执行指令；本报告只据此评估当前项目适配性、优化方案和开发拆分，不修改生产代码。

分析基线：当前 `master` 提交 `f292cba`，项目工作流 `Development OS v1.7`。协议冻结路径为 `Client/protocol.h`、`Server/protocol.h`。

## 2. 结论

方向合适，但不能按附件顺序直接开发。群组聊天（Group Chat，群组聊天）和文件秒传（Fast Upload，快速上传）都与现有产品定位一致，也已在 `project-docs/项目扩展前景.md` 和 `project-docs/融合式扩展功能路线图.md` 中被列为规划能力；当前项目尚未具备可直接承载它们的统一权限、文件资产和幂等状态基础。

本需求整体按 `LARGE`（大规模变更）预评估，原因是：

- 会新增数据库公共模型和跨会话状态；
- 会修改冻结的 PDU（Protocol Data Unit，协议数据单元）枚举与载荷约定；
- 会改变服务端权限、消息广播和文件存储的一致性边界；
- 需要独立测试、修复和只读审计节点，不能用一次普通功能分支覆盖。

推荐先做身份/授权前置门，再并行建设群基础和文件资产，最后分别交付可靠群消息、秒传去重和群文件目录。

## 3. 当前基线与适配性

| 领域 | 当前事实 | 对扩展的影响 |
|---|---|---|
| 协议 | `Client/protocol.h` 与 `Server/protocol.h` 共享枚举，当前业务编号已到 59，PDU 为固定头加柔性载荷 | 新类型只能追加编号；必须版本化载荷、保持旧客户端可解析，触发冻结路径门禁 |
| 服务端分发 | `Server/mytcpsocket.cpp` 按类型调用单体 `MsgHandler` | 群广播、邀请、成员事件不能继续无限堆进一个 switch；需按领域窄接口拆出 `GroupService`（群组服务）或等价模块 |
| 数据库 | 初始化脚本主要包含 `user_info`、`friend`；聊天和外链已有历史表/逻辑，但没有群与文件资产统一模型 | 需提供增量迁移、回滚说明和旧路径兼容，不得直接重建或删除现有用户数据 |
| 聊天 | 一对一消息按发送者/接收者持久化，离线消息以送达状态处理 | 群消息需要群内序号、消息唯一 ID、重试幂等、每成员阅读游标；不能简单复制一对一 SQL |
| 文件 | 用户路径目录、4096 字节顺序分块、连续 offset ACK，服务端异步写临时文件 | 秒传需要物理对象和逻辑文件记录分离；当前上传协议不能直接改成乱序并行 |
| 并发 | socket 列表和在线状态存在跨线程/多连接风险，连接池已有基础但事务边界不统一 | 广播、序号分配、引用计数和上传完成转正必须显式事务/锁/队列 |
| 安全 | 路径穿越已有部分防护；身份主要依赖连接上的登录名，服务端仍有历史 SQL/配置风险 | 群角色、文件所有者和上传者必须由服务端上下文推导，不能信任客户端字段 |

## 4. 对附件需求的逐项判断

### 4.1 群组聊天

适合保留：创建群、邀请、退出、踢人、角色、成员列表、群文本消息、离线消息和未读数量。

必须优化：

1. `group_member(group_id,user_id)` 永久联合唯一约束会阻止离开后重新加入并削弱历史审计。建议保留一条成员主记录并允许 `active/left/kicked` 重激活，或将当前成员和历史事件分表；验收必须覆盖重复邀请、拒绝后再次邀请、离开后重入。
2. `group_invitation` 不能只用三列唯一约束。应有 `invitation_id`（邀请记录唯一标识）和幂等键，唯一约束只限制同一目标的待处理邀请；过期、拒绝和重新邀请必须有明确状态转换。
3. `latest_seq` 与 `last_read_seq` 需要并发定义。推荐事务内锁定群记录后递增序号，消息以 `(group_id,seq)` 唯一；客户端重试使用 `message_id` 幂等，不能靠内容去重。
4. `last_read_seq` 只适合单设备 MVP（最小可用版本）。若保留多设备，需增加 `member_device_read`（成员设备阅读状态）；不能让一台设备覆盖另一台设备的已读位置。
5. 广播不能在数据库事务中逐 socket 阻塞发送。应先提交消息，再通过有界异步发送队列广播；慢客户端需要丢弃/重试策略，不能拖住事件循环。
6. 附件提出的群文件目录不应和群消息首期同时落地；否则会同时引入群权限、路径授权、文件复制和引用计数四套状态。

### 4.2 文件秒传与去重

适合保留：客户端预提交摘要和大小、命中后复用物理对象、未命中继续断点上传、同名冲突由服务端生成展示名。

必须优化：

1. `file_object`（物理文件对象）与 `user_file`（用户逻辑文件条目）应作为正式资产模型，而不是在旧路径表上附加 Hash 字段；这是后续分享、群目录和引用计数的共同基础。
2. `content_hash + file_size` 可作索引和快速筛选，但最终身份建议使用服务端计算的 SHA-256（安全哈希）摘要；客户端摘要只能预检查，不能直接授权秒传。
3. 真实存储路径必须由服务端生成，禁止由 `file_name`、`parent_path` 或客户端 `file_path` 拼接。逻辑目录应使用稳定的 `parent_id`（父目录标识）或受控相对路径。
4. “同名同 Hash 直接复用”需定义幂等边界：同一用户、同一父目录、同一展示名和同一对象的重复请求应返回已有逻辑条目；不同目录仍应产生不同 `user_file` 记录但共用对象。
5. 引用计数、删除和物理回收必须事务化并可恢复；不能因删除一个逻辑条目误删仍被其他用户引用的物理对象。
6. 上传会话应以服务端生成的 `session_id`（上传会话标识）为主键，并绑定当前用户、目标目录、期望大小和摘要；“用户 ID + 目录 + Hash”只能作为幂等校验维度，不能代替会话 ID。
7. 当前连续 offset ACK 不应在本需求中直接升级为乱序并行分片。动态分片和并行上传应另立后续需求，先完成顺序上传的资产转正和校验。

## 5. 推荐范围

### 本期纳入

- 服务端身份/权限上下文和统一成员校验入口；
- 群生命周期、邀请、成员角色、退出/移除和成员列表；
- 群文本消息、按群序号、离线补偿、未读计数、成员事件；
- `file_object/user_file` 基础资产层、旧路径兼容和引用计数；
- 基于现有顺序上传的 Hash 预检查、服务端复算、秒传和同名规则；
- 群文件目录的成员访问、上传、下载和删除权限。

### 本期排除

- 图片、语音、视频、表情等富媒体消息；
- 群消息编辑、撤回、引用、转发、收藏和多设备全量同步；
- 乱序并行分片、动态分片、暂停/恢复任务中心；
- 独立文件服务、对象存储、Redis（缓存/限流服务）和 HTTP 外链；
- 回收站、版本管理、复杂配额和后台运营控制台。

## 6. 分支拆分与依赖

```text
REQ-EXT-SEC-001  服务端身份与授权上下文
        ├── REQ-EXT-GROUP-001  群生命周期与成员关系
        │       └── REQ-EXT-GROUP-002  可靠群文本消息
        └── REQ-EXT-FILE-001   文件资产与内容寻址
                ├── REQ-EXT-FILE-002   顺序上传秒传与去重
                └── REQ-EXT-GROUP-003  群文件目录与访问控制
```

每个 `REQ`（需求编号）为一条独立需求分支；LARGE 节点顺序仍是 goal → design → development → independent test → repair → integration candidate → merge。群文件分支必须等待文件资产分支通过，不能在旧路径模型上提前实现。

## 7. 总体验收与风险

所有分支必须通过旧功能回归：注册/登录、好友、一对一聊天、离线消息、上传/下载/分享/路径防护。数据库迁移必须可在干净库和已有数据上重复执行，失败时不丢失旧文件和消息。

主要残余风险：历史数据库表定义不完整、协议两份头文件人工同步、当前多客户端在线状态模型不足、广播慢客户端背压、Hash 计算耗时以及旧用户路径向逻辑资产迁移的双写一致性。任何一项没有可执行证据时，只能报告 `BLOCKED`（阻塞）或 `CONDITIONAL_PASS`（条件通过），不能提升为通过。
