## 一、审查范围

本次审查聚焦于用户报告的两个问题：
1. 服务端接收加密密码时，密码与验证码在 PDU 中粘连
2. 验证码过期逻辑不纯（应完全基于过期时间判断）

## 三、审查结果

### 缺陷 1：BUG-REV-AUTH-001（一般）— MD5 密码哈希缺少 null 终止符

**根因**：客户端 `copyExactField(pdu->caData+32, 32, passwordHash)` 将 32 字节 MD5 哈希填入 caData 的 32 字节槽位，不留 `\0`。与 `copyFixedField`（用于用户名，保留 1 字节给 `\0`）形成不一致。

**影响**：
- 服务端 `mytcpsocket.cpp:316-317` 中 `qDebug() << pdu->caData+32` 作为 C 字符串打印时越界读入 caMsg（验证码），日志显示 `MD5密码+验证码`，造成"粘连"假象
- 当前功能逻辑因 `fixedString()` 限界 32 字节的保护而未出错，但存在未来回归风险
- 客户端 `seedMsg()` 的 `qDebug` 存在同样的调试输出缺陷

**状态**：`已确认，待修复` → 移交工程师处理

---

### 缺陷 2：BUG-REV-AUTH-002（严重）— 验证码逻辑未纯基于过期时间

**根因分两部分**：

#### 2a. 重复请求覆盖旧验证码（核心问题）
`captcha()` 函数无条件覆盖 `m_captcha`：
```cpp
m_captcha.first = generateCaptchaCode(6);   // 覆盖！
m_captcha.second = QDateTime::currentDateTime().addSecs(60);
```
导致：用户快速点击两次"获取验证码"后，第一次生成的验证码（仍在有效期内）被覆盖失效。

#### 2b. isEmpty() 误判为"过期"
```cpp
if (m_captcha.first.isEmpty()) {
    return -3;  // 与"已过期"相同错误码
}
```
将"验证码不存在/上下文丢失"与"验证码已过期"混为一谈。

**影响**：
- 用户验证码在有效期内却无法使用，反复重试失败
- 登录/注册流程均受影响
- 用户体验恶化

**状态**：`已确认，待修复` → 提交架构师确认修复方向（数据结构变更需架构批准）

## 四、剩余风险

1. **`fixedString` 之外是否还有代码直接以 C 字符串方式读取 `caData+32`**：经搜索，当前服务端仅有 `rigist()` 和 `login()` 使用 `fixedString` 读取密码，未见其他裸读路径。但若未来新增代码绕过 `fixedString`，BUG-REV-AUTH-001 的风险将升级为功能性 bug。
2. **客户端 `SimpleCaptcha` 与服务端验证码的混淆**：客户端存在本地 `SimpleCaptcha` 组件（独立生成验证码），与服务端 `captcha()` 生成的验证码是完全独立的两个系统。当前客户端使用的是服务端验证码（`captcha()` 返回的），`SimpleCaptcha` 组件似乎未被使用。需确认是否为遗留代码或存在预期外的交互。
