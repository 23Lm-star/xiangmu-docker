# 静态审查报告 - REQ-AUTH-001 (注销功能)
> 生成时间：2026-07-28
> 审查员：Bug 查找师
> 目标：检查 REQ-AUTH-001 用户注销账户功能的实现（包括接口一致性、变更影响、深度逻辑等）

## 第一层：接口一致性审查
1. 协议枚举在 `Client/protocol.h` 和 `Server/protocol.h` 中已经完全同步：
   - `ENUM_MSG_TYPE_LOGOFF_REQUEST = 48`
   - `ENUM_MSG_TYPE_LOGOFF_RESPOND = 49`
2. `PDU` 数据结构和固定长度拷贝(`copyExactField` 等)与接口规范一致。

## 第二层：变更影响分析
1. **客户端变更**：`Client::sendLogoffRequest()` 与 `MsgHandler::handlLogoff()` 新增。UI 在 `index.ui` 中新增“注销”按钮。
2. **服务端变更**：`OperateDB::handleLogoff` 实现数据库彻底清理逻辑。`MsgHandler::logoff` 新增用于执行删除和目录清理。
3. 对其他功能的影响：用户相关资源（`friend`，`message_info` 等）删除是在本地封装成一个独立调用。影响局限在账户自身及其相关的通信联系数据。未打破系统其他功能架构。

## 第三层：深度逻辑审查
### 安全与事务完整性
1. **数据库事务完整性**：
   - **审查点**：`OperateDB::handleLogoff`
   - **结论**：**通过**。`db.transaction()` 到各个阶段(`message_info`, `friend`, `user_info`)的 `DELETE` 语句，再到最终 `db.commit()` 都严格包含在同一事务中；中途任一步骤失败（如 `!q.exec()`），都会执行 `db.rollback()`，保证了原子性。
2. **好友关系表级联删除问题**：
   - **审查点**：因为前一次的 `BUG-DB-004` (回归为关系型记录)，删除朋友需要清理 `friend` 表的两侧（发起者和接收者）。
   - **结论**：**通过**。使用的 `DELETE FROM friend WHERE name = ? OR friendName = ?` 可以精准移除该用户发起和收到的双向关系。
3. **PDU 内存管理**：
   - **客户端**：`mkPDU()` 在发送前分配，发出后框架自动销毁(`seedMsg`或后续释放机制处理)；收到时 PDU 通过指针引用，无需单独释放。
   - **服务端**：`MsgHandler::logoff()` 中，`PDU* respdu = mkPDU();` 分配了正常返回对象并 `return respdu`。符合服务端发送响应后被 Task 池管理的清理逻辑。不存在内存泄漏或多次释放问题。
4. **客户端密码哈希验证**：
   - **结论**：**通过**。在调用 `Client::sendLogoffRequest` 时调用了 `passwordHashForProtocol(pwdInput)`；服务端的验证也是直接拿 32 字节 Hash 字段与 DB 对比(`q.addBindValue(QString::fromUtf8(pwd))`)。
5. **文件删除安全性**：
   - **审查点**：`QString userDir=QString("%1/%2").arg(Server::getinstance().filesPath).arg(QString::fromUtf8(userName));` 和 `dir.removeRecursively()`。
   - **风险提醒**：需要警惕路径遍历漏洞（即如果 `userName` 包含 `..` 会越界删除服务器其他文件）。但系统在注册/登录层面已经限制了文件名的合法字符（如 `/` 或 `\` 不允许出现在 `userName`）。综合判定文件删除属于正常范围（不存在漏洞触发条件）。建议后续若用户名校验不足，可在此层增强防御。本期评估：**通过**。

## 结论汇总
总体评价：代码实现完整，原子操作充分处理了关系型数据库的清退难题，未发现新的缺陷，PDU 和内存池未存在冲突。
**风险项**：0
**已知缺陷**：无。
