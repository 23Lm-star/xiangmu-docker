### BUG-POOL-001 — MyTcpSocket::handlMsg 中 uploadfiledata 返回的 PDU 在循环中处理时存在 double-free(二次释放) 风险

| 字段 | 内容 |
|------|------|
| **严重等级** | **严重** |
| **涉及模块** | `Server/mytcpsocket.cpp` |
| **代码位置** | `MyTcpSocket::recvmsg()` 第 269-271 行 |
| **触发条件** | 非最后一块文件数据上传时 |
| **问题说明** | 在 `recvmsg()` 循环中，`handlMsg(pdu)` 返回的 respdu 被传递给 `seedMsg(respdu)`，而 `seedMsg()` 会调用 `memfree(respdu)` 释放内存。但 `uploadfiledata()` 在上传未完成时（`ret && !m_uploadSession.isComplete()`）**返回 nullptr**，同时 `uploadfiledata()` 在数据完整时返回一个**新建的 PDU**，类型为 `ENUM_MSG_TYPE_UPLOADFILE_DATA_RESPOND`。此时循环继续执行 `seedMsg(respdu)` 正常释放。**问题在于**：如果 `uploadfiledata()` 返回的是最后一块数据的确认 PDU，多次 `seedMsg` 调用处理多个完整 PDU 时，每个都独立构建和释放，逻辑上看起来正确，但存在一个**隐藏风险**：`handlMsg` 对 `DOWNLOADFILE_REQUEST` 的特殊处理（第 139-151 行）中，手动调用了 `seedMsg(respdu)` 并将 `respdu` 置为 nullptr 后又 `return nullptr`。搜索模式不统一，如果在后续扩展中其他 case 也手动发送后又返回非空 PDU，将导致二次释放。 |
| **预期行为** | 所有 case 返回的 PDU 要么全权交由 `recvmsg()` 循环统一释放，要么在 case 内部释放后返回 nullptr，不应混合两种模式。 |
| **影响范围** | `DOWNLOADFILE_REQUEST` 路径存在手动调用 `seedMsg` 后又返回非空的风险。当前代码通过 `return nullptr` 规避了二次释放，但模式不统一，维护风险高。 |
| **判断依据** | 代码审查。`handlMsg` 中第 139-151 行的 DOWNLOADFILE_REQUEST 分支手动调用 seedMsg 发送，又返回 nullptr，与其他 case 的返回模式不一致。 |
| **修正建议** | 统一 `handlMsg` 的 PDU 所有权管理方式：要么所有 case 都通过返回值由调用方释放，要么对需要手动发送的 case 统一返回 nullptr。推荐将 DOWNLOADFILE_REQUEST 改为返回 respdu，删除内部的 `seedMsg(respdu)` 调用和 `respdu=nullptr` 赋值，让 `recvmsg` 循环统一处理。 |
| **建议验证方式** | 静态审查确认模式统一后即可关闭。 |
| **当前状态** | 待确认 |

### BUG-POOL-003 — Server 端 seedMsg 使用 memfree 释放 pdu，Client 端 seedMsg 使用 free，内存管理不一致

| 字段 | 内容 |
|------|------|
| **严重等级** | **严重** |
| **涉及模块** | `Server/protocol.cpp` vs `Client/protocol.cpp` |
| **代码位置** | Server: `protocol.cpp` 第 9 行 (`memalloc`)；Client: `protocol.cpp` 第 10 行 (`malloc`) |
| **触发条件** | Server 端收到 Client 请求的全部场景 |
| **问题说明** | Server 端的 `mkPDU()` 使用 `memalloc()`（来自自定义内存池）分配内存，`seedMsg()` 使用 `memfree()` 释放。Client 端的 `mkPDU()` 使用标准的 `malloc()` 分配，`seedMsg()` 使用标准的 `free()` 释放。**但 Server 端 `MyTcpSocket::recvmsg()` 接收到的数据来自 Client 端的 `malloc`/`free` 系列**：接收缓冲区 `m_dpulist` 中存储的是原始字节流，通过类型强转 `(PDU*)m_dpulist.data()` 获得的 PDU 指针指向的是 QByteArray 内部缓冲区，**不需要也不应该被释放**。问题在于 `handlMsg` 收到的 pdu 参数是从 QByteArray 强转而来，`handlMsg` 调用的 `m_MsgHandler->pdu=pdu` 将栈/堆上构造的 PDU 引用传递给了各 handler 函数。这些函数读 `pdu->caMsg` 等字段，没有跨模块释放问题。但需要注意的是：Client 端(login.cpp:238) `seedMsg` 使用 `free(pdu)`，而 Server 端 `seedMsg` 使用 `memfree(pdu)` —— 跨端通信时，内存由各自端的 `mkPDU` 分配，不会交叉释放，所以当前不会触发运行时错误。但**架构上不统一**，如果未来任何一端混淆了 `malloc`/`free` 和 `memalloc`/`memfree` 的混用，会直接导致崩溃。 |
| **预期行为** | 两端应使用一致的内存分配/释放策略，或者在架构师层面明确内存管理所有权策略。 |
| **影响范围** | 全部 PDU 相关操作。当前因两端各自管理自己的内存，功能不受影响，但易因后期维护引入 bug。 |
| **判断依据** | 代码审查。Server 端 `protocol.cpp` 使用了 `memalloc`，Client 端使用了 `malloc`。 |
| **修正建议** | 建议两端的 `mkPDU` 统一内存分配策略。推荐两套方案：方案 A：两端都使用标准的 `malloc`/`free`（简化架构，移除 Server 端自定义内存池依赖）。方案 B：两端都使用 `memalloc`/`memfree`（保持内存池一致）。需架构师决策。 |
| **建议验证方式** | 采用方案后运行 full test，确保没有内存泄漏或崩溃。 |
| **当前状态** | 待确认 |

### BUG-POOL-004 — login() 返回值错误：handleLogin 返回 int，但最终被隐式转换为 bool

| 字段 | 内容 |
|------|------|
| **严重等级** | **严重** |
| **涉及模块** | `Server/operatedb.cpp` |
| **代码位置** | `OperateDB::handleLogin()` 第 81 行 |
| **触发条件** | 用户登录成功时 |
| **问题说明** | `handleLogin()` 函数签名为 `int handleLogin(...)`，应返回：`0` 表示其他错误，`-1` 表示密码错误，`1` 表示登录成功。但第 81 行使用了 `return q.exec()`，`q.exec()` 返回 `bool` 类型（SQL UPDATE 是否成功）。`true` 被隐式转换为 `1`，功能上巧合正确，但语义错误：如果 SQL UPDATE 失败，理应返回 `0` 但 `q.exec()` 返回 `false` 被隐式转换为 `0`，功能正确但不符合设计意图。更重要的是：第 79 行的 qDebug 注释显示本意是区分"密码验证失败"(-1)和"更新 online 状态失败"(0)，但当前通过 `return q.exec()` 丢失了这种区分。 |
| **预期行为** | 登录验证成功后应明确返回 1，UPDATE 失败时应返回 0（不表示登录失败，而是状态更新失败）。 |
| **实际行为** | `return q.exec()` 将 bool 隐式转 int，语义不明确。 |
| **影响范围** | 服务端登录逻辑，客户端将看到 `handllogin()` 中的 `ret==1` 分支和 `else` 分支。UPDATE 失败时客户端将显示"状态异常"而非明确的数据库错误。 |
| **判断依据** | 代码审查。函数返回值语义混用：`int` 类型但返回了 `bool`。 |
| **修正建议** | 改为：明确区分错误类型。建议将第 81 行改为两步：`bool updateOk = q.exec(); return updateOk ? 1 : 0;` |
| **建议验证方式** | 测试数据库连接断开时登录的场景。 |
| **当前状态** | 待确认 |

### BUG-POOL-005 — ClientTask::run() 为空函数，线程池资源被浪费

| 字段 | 内容 |
|------|------|
| **严重等级** | **一般** |
| **涉及模块** | `Server/clienttask.cpp` |
| **代码位置** | 第 10-13 行 |
| **触发条件** | 每个新客户端连接时 |
| **问题说明** | `ClientTask::run()` 函数体为空。`MyTcpServer::incomingConnection()` 每接收一个新连接就创建一个 `ClientTask` 并提交到线程池 `m_threadPool.start(task)`。但 `ClientTask::run()` 什么都没做。实际的请求处理是通过 `MyTcpSocket` 的信号/槽机制在主线程的事件循环中完成的，线程池完全浪费。 |
| **预期行为** | 要么 `ClientTask` 真正在线程池中工作（处理 PDU 需要在线程中执行），要么移除线程池机制，全部使用 Qt 的事件驱动模型。 |
| **实际行为** | 为每个连接创建了空工作的 `ClientTask`，浪费线程池资源。 |
| **影响范围** | 每新建一个客户端连接，线程池中的一个线程被占用但做无用功，浪费系统资源。 |
| **判断依据** | 代码审查。`ClientTask::run()` 函数体为空。 |
| **修正建议** | 方案 A：将 `MyTcpSocket` 的实际工作代码（`recvmsg` 中的处理逻辑）移入 `ClientTask::run()` 中，让处理在线程池中完成。方案 B：移除 `ClientTask` 和线程池的使用，完全依赖 Qt 事件驱动。需架构师决策。 |
| **建议验证方式** | 修改后测试多客户端并发场景。 |
| **当前状态** | 待确认 |

### BUG-POOL-006 — Server 端 loadconfig 中 QMessageBox::critical 在非 GUI 线程使用有潜在风险

| 字段 | 内容 |
|------|------|
| **严重等级** | **一般** |
| **涉及模块** | `Server/server.cpp` |
| **代码位置** | `Server::loadconfig()` 第 38-43 行、第 49-50 行 |
| **触发条件** | 配置文件格式不正确或打开失败时 |
| **问题说明** | `loadconfig()` 在 `Server` 构造函数中调用，此时 GUI 事件循环应该已经启动（在 `main()` 的 `QApplication a(argc, argv)` 之后），所以此处使用 `QMessageBox` 理论上不会直接崩溃。但存在两处问题：(1) `exit(1)` 是硬退出，没有正确清理 Qt 资源；(2) 如果作为无头服务启动，`QMessageBox::critical` 会卡住。 |
| **预期行为** | 配置失败时应通过 `qCritical()` 记录日志后 `exit(1)` 或通过 `QApplication::quit()` 优雅退出，不应依赖 UI 弹框。 |
| **实际行为** | 配置失败时弹出 `QMessageBox` 弹框。 |
| **影响范围** | 无头模式（无显示器）下运行服务端将卡死在弹框处。 |
| **判断依据** | 代码审查。 |
| **修正建议** | 在 `loadconfig()` 中只使用 `qCritical()` 记录错误日志，移除 `QMessageBox::critical` 调用，然后在 `main()` 中检查配置结果决定是否退出。或者将配置错误检查移出构造函数，用一个返回 bool 值的 init() 函数处理。 |
| **建议验证方式** | 在无显示器环境中运行服务端，配置错误时应正常退出而非卡死。 |

## 总体结论

项目在基础功能架构上较为完整，本次新增的数据库连接池功能实现基本正确。主要问题集中在：

1. **内存管理策略不统一**（BUG-POOL-003, BUG-POOL-007）：Server 端使用自定义内存池，Client 端使用标准 malloc/free，两端 `mkPDU`/释放模式不一致，存在长期维护风险。
2. **线程池虚耗**（BUG-POOL-005）：`ClientTask::run()` 为空函数，每条连接浪费线程资源。
3. **代码质量**（BUG-POOL-002, BUG-POOL-004, BUG-POOL-008）：拼写错误、返回值语义混淆、注释乱码。
4. **配置加载缺陷**（BUG-POOL-006）：UI 弹框可能导致无头模式卡死。

建议架构师优先决策 BUG-POOL-003（内存管理策略统一方案）和 BUG-POOL-005（线程池去留方案），然后工程师依次修复。
