## 二、架构裁定

### BUG-SEC-003 裁定：**批准。计数器容错优于立即断开。**

理由：

1. **公网环境适配**：TCP 流中因网络噪声、MTU 碎片、中间设备故障等导致的偶发性字节损坏在公网是正常现象。立即断开合法客户端会严重影响可用性。
2. **自愈能力**：合法 PDU 后重置计数器（line 308）使连接具备自我修复特性。如果客户端恢复同步，连接可继续正常使用。
3. **安全底线坚实**：256KB 硬上限（line 265-271）始终存在，即使攻击者保持非法 PDU 但不触发 5 次阈值，也无法无限堆积内存。
4. **阈值合理**：5 次连续非法是生产环境中常见的设值（如 nginx `max_errors`、SSH `MaxAuthTries`），兼顾防护与可用性。
5. **测试师模拟推演通过**：包长度对齐、计数器清零、熔断触发逻辑均确认无死循环。

**与 R03 决策的关系**：R03 中的"立即断开"是基于当时的项目阶段（内网/LAN 环境）的合理决策。随着项目向公网部署演进，计数器容错是 R03 的自然升级，不视为对 R03 的否定。

### BUG-DB-004 裁定：**批准。关系型回归优于 JSON 聚合。**

理由：

1. **简洁性压倒一切**：UNION + INSERT + DELETE 是标准 SQL，开发者无需理解 `JSON_CONTAINS`、`JSON_SEARCH`、`JSON_REMOVE` 等 MySQL 特有函数。
2. **索引效率**：`UNIQUE KEY(name, friendName)` 可利用标准 B-tree 索引，JSON 内的数组查找无法简单走索引。
3. **代码可审计性**：三句 SQL 即可完整理解好友增删查逻辑，JSON 方案需要理解 MySQL JSON 路径表达式。
4. **事务完整性保持**：`handleAddFriendFin` 和 `handleDeleteFriend` 均包裹在 `db.transaction()` 中。

**与 R03 决策的关系**：R03 采用 JSON 聚合的出发点"控制单表行数膨胀"在项目当前阶段（用户量级 < 万级）是过度优化。关系型方案在万级用户下完全可支撑，且更易于后续扩展（如添加好友备注、分组等字段）。若未来确实需要 JSON 聚合，迁移路径明确：`SELECT DISTINCT name FROM friend` 按用户聚合即可。

### 发现事项：外键约束缺失

`friend` 表缺少对外键 `user_info` 的引用级联约束。

**裁定**：考虑到当前系统完全未提供**“注销/彻底删除用户”**功能（`handleOffLine` 仅将 online 标记为0），孤儿好友记录在当前业务闭环内不会发生。我们接受目前应用层一致性保证的现状。未来开发注销功能时连同解决。目前 BUG-DB-004 已标记为**已接受风险**。
