# ADR-013: Large Transfer Backpressure and Heartbeat Responsiveness

## Status

Implemented on 2026-07-30.

## Context

The control protocol, file upload, file download, and heartbeat share one TCP socket per client. The previous uploader emitted every chunk immediately and the server download stream continuously appended chunks without observing the socket write buffer. Server-side upload writes also ran in the socket event loop.

## Decision

- Keep the existing event-driven model: one server event thread owns all `MyTcpSocket` instances. Do not add a thread per connection.
- Upload uses one acknowledged 4 KB chunk at a time. The client sends the next chunk only after an upload response supplies the next confirmed offset.
- `UploadWriteTask` writes each accepted chunk on `QThreadPool`. It returns through a queued `MyTcpServer` callback identified by connection ID; worker threads never call `MyTcpSocket::write()`.
- Download stops scheduling chunks when `bytesToWrite()` would exceed 256 KB and resumes after `bytesWritten` drains the buffer.
- PING/PONG keeps the existing message type and uses the same socket. The changes bound its delay behind application queued file data; TCP bandwidth saturation remains a physical limit.

## Impact

- Modified: Client uploader/file response path; server upload session, socket, server dispatcher, and build project.
- Protocol compatibility: client and server must be deployed together because upload data responses now include confirmed offset and completion state.
- Risk: stop-and-wait upload lowers high-latency throughput. It is deliberately chosen as the smallest reliable window; a future sliding window can increase throughput while retaining a bounded in-flight byte budget.

## Verification

- Rebuilt both `Server.pro` and `Client.pro` with Qt 5.14.2 and MinGW 7.3 successfully.
- Runtime transfer verification requires a configured MySQL service and two logged-in test accounts; it was not run in this workspace.
