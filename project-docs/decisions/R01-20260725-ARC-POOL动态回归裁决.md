# 决策记录：POOL-001~008 动态回归裁决与 BUG-TST-CLIENT-001 处理方向

> 背景：项目测试师完成 `project-docs/test-reports/R01-20260725-TST.md`，POOL-001~008 回归验证通过，但发现 Client 登录后文件列表加载崩溃。

## 问题描述

1. POOL-001~008 已完成二次审查、构建验证与可执行范围内的动态回归。
2. Server 端可启动、监听 `127.0.0.1:5000`，数据库连接成功，注册/登录/好友列表/文件列表请求响应正常。
3. Client 登录成功后收到 `FLUSHFILE_RESPOND`(24)，在 `MsgHandler::flushfile()` → `File::updateCurrfile()` 过程中或之后崩溃，运行时输出：`pure virtual method called` / `terminate called without an active exception` / exit code 3。
4. `interfaces.md:35` 与 `code-map.md` 仍残留 `Msg::totoalLen` 旧字段名，已与代码事实冲突。

## 决策

### D1：POOL-001~008 本轮视为已验证通过

POOL-001~008 均保持 `已修复` 状态：

- 直接运行时相关的 Server 启动生命周期、登录响应、协议兼容性和构建均已通过验证。
- POOL-003、POOL-007 为纯注释/文档禁测区域，不要求动态执行。
- Client 崩溃发生在登录成功后文件列表 UI 更新阶段，测试报告判定为非 POOL 修复引入；不回退 POOL 已修复结论。

### D2：BUG-TST-CLIENT-001 确认为严重缺陷，立即分配工程师修复

BUG-TST-CLIENT-001 从 `待确认` 更新为 `已确认，待修复`。

本缺陷不得降级为“已确认，可继续测试，修复延后”，理由：

- 它完全阻塞 Client 端全链路动态测试，包括文件下载、并发、多功能联调等质量门禁项目。
- 现象为进程崩溃（SIGABRT），属于核心客户端可用性失败。
- 即使非 POOL 引入，也会影响当前项目整体交付门禁。

### D3：完整质量门禁暂不通过；Server 侧门禁局部通过

- Server 侧：本轮 POOL 相关 Server 动态验证通过。
- Client 侧：被 BUG-TST-CLIENT-001 阻塞。
- 完整项目门禁：不通过，直至 BUG-TST-CLIENT-001 修复并完成 Client 侧回归。

### D4：治理文档同步修正

立即同步：

- `project-docs/interfaces.md`：`Msg::totoalLen` → `Msg::totalLen`。
- `project-docs/code-map.md`：更新 ClientTask/POOL 风险状态，更新 Msg 数据模型字段，新增 BUG-TST-CLIENT-001 风险区域。
- `project-docs/defects/README.md` 与 `project-docs/defects/BUG-TST-CLIENT-001.md`：同步状态和裁决。

## 理由

1. Client 崩溃是可复现、可定位到响应处理阶段的运行时故障，不属于单纯测试环境不稳定。
2. “pure virtual method called” 通常指向 QObject 生命周期、析构期信号槽、悬挂指针或虚函数表破坏；需要工程师读取 `Client/file.cpp`、`Client/msghandler.cpp`、`Client/index.cpp`、相关 UI 生命周期代码做根因修复。
3. 当前 POOL 修复已有静态审查、构建、Server 动态证据支撑，不能因独立预存 Client 缺陷否定已验证结果。
4. 文档与代码冲突会误导后续 Agent，必须由架构师同步唯一事实来源。

## 未来改进方向

1. Client 主界面初始化期间避免构造函数内立即发送依赖网络响应的请求；如需刷新文件列表，应在对象完全构造并显示后以明确生命周期时机触发。
2. `MsgHandler` 访问 `Index::getinstance().getFile()`、`getFriend()` 等 UI 单例前，应确保目标对象仍有效并处于可更新状态。
3. 为 Client 登录后首屏加载建立最小动态回归用例：登录成功 → 刷新好友 → 刷新文件 → UI 可继续交互。
