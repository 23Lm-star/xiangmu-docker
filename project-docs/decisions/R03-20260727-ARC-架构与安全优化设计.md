### 1. 数据库关系表优化（好友表重构）
*   **决策**：同意采用 `JSON` 聚合存储的方式替换双向 `1 对 1` 行记录（方案 A）。
*   **理由**：用户明确提出控制单表行数膨胀的需求。在关系型表结构下，改为 `[user_id, friend_list(JSON)]` 后可以确保 N 个用户最多产生 N 行记录。
*   **实现要求**：
    *   `project-docs/interfaces.md` 已同步更新。
    *   工程师必须提供可重复执行的迁移方案：备份旧表 → 建立 JSON 新表 → 从旧 `friend(user_id,friend_id)` 聚合迁移 → 校验行数/好友数 → 原子切换；未经验证不得删除旧数据。
    *   `handleAddFriendFin` 与 `handleDeleteFriend` 必须在单一数据库事务中同步更新双方 JSON 数组，并保证重复添加不会产生重复 ID。
    *   `handleFlushFriend` 与 `handleOnlineUsers` 必须改用 MySQL JSON 查询；任何不支持 JSON 的数据库版本应明确失败并回滚迁移。

### 2. TCP 层协议包长度熔断机制
*   **决策**：采用强硬边界截断，防止服务器因恶意报文 OOM（方案 B 修改版）。
*   **阈值设定**：单包最大长度限制定为 `16 KB`（即 `16384 Bytes`）。因为现有文件传输业务基于 4096 字节的分块进行传输，16K 为数据块与各类元数据留有了充足的容错和缓冲空间。
*   **实现要求**：
    *   在 `Server/protocol.h` 定义 `MAX_INBOUND_PDU_SIZE = 16 * 1024`，仅作为 C→S 入站限制；不得修改 `DOWNLOAD_CHUNK_SIZE = 65536` 或为服务端→客户端的下载响应施加该限制。
    *   在 `MyTcpSocket::recvmsg()` 的 `m_dpulist.append(readAll())` 后执行累计缓存上限检查：`MAX_PENDING_INBOUND_BYTES = 256 * 1024`。该上限只约束当前未处理的内存积压，**不限制单连接累计文件大小或累计 PDU 数量**。
    *   在读取完整 PDU 前验证 `sizeof(PDU) <= uiTotalLen <= 16384`、`uiMsgLen == uiTotalLen - sizeof(PDU)` 和合法 `uiType`；失败时记日志、清空缓存、`disconnectFromHost()` 并返回。
    *   每个完整 PDU 必须在处理后立即从 `m_dpulist` 移除；上传数据块由既有 `ResumableUploadSession` 立刻写入磁盘，以支持 GB 级文件分块传输。
