# 架构师裁决：BUG-DB-004 / BUG-SEC-003 关闭门禁与转发 PDU 泄漏

> 批次：R14
> 裁决日期：2026-07-27
> 裁决人：项目架构师
> 输入：测试师口头/交接结论、`SECONDARY-REVIEW-20260727-REV-DB004-SEC003.md`、当前源码与工作区事实。

## 一、已确认事实

1. `OperateDB::handleAddFriendFin()` 与 `handleDeleteFriend()` 均以单个数据库事务包裹双方 JSON 数组写入，失败路径回滚；添加路径含 `JSON_CONTAINS` 幂等保护。源码：`Server/operatedb.cpp:180-355`。
2. Server 入站路径定义了 `MAX_INBOUND_PDU_SIZE = 16 * 1024` 和 `MAX_PENDING_INBOUND_BYTES = 256 * 1024`，在解析前实施水位线、长度、消息体一致性和类型范围校验。源码：`Server/protocol.h:66-67`、`Server/mytcpsocket.cpp:258-310`。
3. Bug 查找师已完成二次静态审查并把两项置为“已修复”。证据：`project-docs/bug-reports/SECONDARY-REVIEW-20260727-REV-DB004-SEC003.md:261-283`。
4. 当前 `project-docs/test-reports/` 及其 README 没有 BUG-DB-004 / BUG-SEC-003 的正式回归报告索引；用户转述的安全证据为 Python 模拟攻击，并非真实 Server 动态攻击/断连日志。
5. 当前分支 `add_数据库连接池功能` 相对 `master` 存在大量未提交、非本批次混合改动与删除；不可将“合并分支”理解为只合并这两项缺陷的干净变更集。

## 二、关闭门禁裁定

### BUG-DB-004

**裁定：维持“已修复”，不关闭。**

代码和二次静态审查满足修复存在、接口/数据模型实现正确的门禁；但尚无可读取的正式动态回归报告来证明真实 MySQL 迁移、好友双向增删、重复添加、空列表及失败回滚。测试师须补交真实环境报告后，再提交关闭申请。

### BUG-SEC-003

**裁定：维持“已修复”，不关闭。**

代码和二次静态审查满足实现门禁；Python 模拟不能替代真实 Server 进程对超长包、字段不一致包、非法类型包和慢速积压的断连/日志证据。测试师须以本分支重新构建的 Server 进行真实 socket 动态测试并归档结果，之后才能申请关闭。

> 本裁定不否定测试师已发现的正向迹象；仅拒绝将不足以支撑关闭的转述/模拟证据提升为最终交付证据。

## 三、独立新缺陷：BUG-ARC-NET-001

### 裁定：立即修复（一般）

`MsgHandler::addfriend()` 在在线目标路径分配的转发 PDU 经 `seedAddFriend()` 写出后未释放，且返回 `nullptr` 跳过 `recvmsg()` 释放逻辑。源码：`Server/msghandler.cpp:196-202`、`Server/mytcpserver.cpp:43-55`。修复必须新增仅供此路径使用的单次拥有型转发接口；不得令既有借用型 `seedAddFriend()` 释放 PDU，因为 `addfriendFin()` 用同一 PDU 连续转发给两端。

这不是本批 DB/SEC 修复引入的问题，也不回退 BUG-DB-004/BUG-SEC-003 的“已修复”状态；但会随在线添加好友操作累积内存，因此在向 `master` 合并前必须完成最小所有权修复、二次静态审查和回归。

## 四、合并裁定
