## 2. 需求分析总结

### 2.1 业务目标

建立群生命周期和成员关系的唯一服务端事实源，支持：建群、邀请、接受、拒绝、主动退出、移除成员、角色任免、群主转让、解散、成员列表和群摘要查询。客户端只展示结果，所有权限和状态转换由服务端判定。

### 2.2 数据模型与状态约束

- `group_info`（群基本信息）：群标识、名称、创建者、群状态、版本号、创建时间。
- `group_member`（群成员关系）：群标识、用户标识、角色、成员状态、加入时间、更新时间、`last_read_seq`（后继群消息使用的未读游标）。保留群内唯一约束，并增加 `(user_name, group_id)` 联合索引，支持按用户快速获取“我的群聊”列表；成员离开采用状态变更，保留历史行并允许重新激活。
- `group_invitation`（群邀请）：独立邀请标识、群标识、邀请人、目标用户、邀请状态、过期时间、创建/处理时间和幂等键。
- 有效成员必须由数据库约束和事务共同保证唯一；接受、移除、重入的竞争结果必须确定，不能产生两个有效成员状态。
- 解散采用状态置为已解散，保留成员和历史数据；解散后拒绝任何写操作，允许读取既有历史，供 GROUP-002/003 统一拒绝已解散群写入。

### 2.3 权限矩阵

- 群主：成员管理、角色管理、资料修改和解散。
- 管理员：邀请、移除普通成员、查看成员；不能移除群主或其他管理员，不能转让群主或解散。
- 普通成员：查看群资料/成员、主动退出。
- 所有请求的操作者身份来自连接级 `actor`（服务端认证主体），不信任客户端自报用户名；未知群、非成员和越权请求统一拒绝。

### 2.4 协议与触达

- 两份协议头文件的旧枚举保持不变；群类型只能从现有 59 之后追加。
- 每个新请求和响应使用显式版本、载荷长度和 `request_id`（请求唯一标识）字段，不直接传输带编译器填充的 C++ 结构体。
- 在线成员变化使用 `fan-out`（向多个在线成员广播）事件；事件发送失败不能回滚已提交的成员状态。
- 登录过程不主动拉取群邀请、群摘要或群消息；进入群聊模块时按需查询未处理邀请和群列表，打开具体群聊时再拉取消息和未读摘要，作为在线事件的持久化兜底。
- 新旧客户端遇到未知类型必须得到明确拒绝，不能误解释成旧业务消息。

### 2.5 不包含内容

本需求不实现群消息正文、群文件上传/删除和群公告；这些功能分别留给 GROUP-002/003，且只能依赖本需求稳定的成员和解散状态语义。

## 3. 现有实现对接点

- 协议入口：`Server/mytcpsocket.cpp` 的统一认证门和消息分发；新增群请求挂入现有分发后自动继承连接级认证上下文。
- 数据层：`Server/operatedb.{h,cpp}` 和 `DatabaseConnectionPool`（数据库连接池）提供事务与连接生命周期基线；现有好友关系写入已使用事务，但群成员不能复用双向好友表。
- 数据库版本：当前 `schema_version`（数据库版本表）由 FILE-001 启动检查；GROUP-001 必须使用新的独立迁移脚本、回滚脚本，并把目标版本纳入现有单调版本检查。
- 在线推送：`MyTcpServer` 现有单目标同步写入模式；本需求需扩展为多成员遍历，并在设计节点明确慢连接和多连接策略。
- 客户端：现有 `Client/msghandler.cpp` 和 `Index`（主界面单例）没有群 UI；需要新增与好友、文件同级的群聊模块，内部提供群列表、成员、邀请和群聊窗口，按界面打开时发起查询；不得改变好友、一对一聊天和旧文件协议语义。

## 4. 分阶段实施计划

### 阶段 A：批准前（当前阶段）

1. 主人审阅本分析和计划，确认允许进入 design（设计节点）与开发。
2. 获得批准后重新运行 `pipeline/state.ps1`，确认 `master` 无挂起状态、当前基线和待处理审计报告已记录。
3. 从批准时的 `master` 头创建 `codex/req-ext-group-001-membership`；不从旧分支或 GROUP-002 分支切出。

### 阶段 B：design（设计节点）

1. 输出 `project-docs/tasks/REQ-EXT-GROUP-001/design.md`：表结构、状态机、索引/唯一约束、事务锁定顺序、解散只读规则和迁移回滚方案。
2. 输出 GROUP-001 与 GROUP-002 共用的 PDU（协议数据单元）编号表，从 60 起连续追加；列出请求/响应方向、版本、长度、请求唯一标识和未知类型拒绝行为。
3. 固化服务端权限矩阵和每个操作的失败码；明确操作者来自 `actor`，群标识不能作为越权读取入口。
4. 固化在线广播、按需查询、重试幂等和多连接策略；事件失败只记录，不撤销已提交事务，登录流程不增加群数据拉取。
5. 把验收标准映射到自动化探针、数据库断言和旧业务回归清单；设计节点完成后再进入源码开发。

### 阶段 C：development（开发节点）

1. 数据迁移：新增三张群表及必要索引、幂等迁移和回滚；更新现有 `schema_version` 目标版本，服务端低版本继续 fail-fast（启动失败并给出迁移提示）。
2. `OperateDB` 窄接口：建群事务、邀请幂等、接受/拒绝、成员激活/退出/移除/重入、角色变更、转让、解散、成员列表、邀请与群摘要查询。
3. 协议与入口：两份 `protocol.h` 只追加编号和定长/长度校验辅助定义；在 `MyTcpSocket`/`MsgHandler` 加入认证请求分发、未知类型拒绝和服务端操作者覆盖。
4. 权限与并发：每个写操作在同一数据库事务内完成状态校验和更新；并发接受/移除使用一致的行锁和条件更新，确保最终只有一个有效成员。
5. 事件与客户端：在线成员广播、群聊同级模块、界面触发的群列表/邀请/成员查询，以及具体群聊打开后的消息查询入口；保留旧客户端登录、好友、一对一聊天和旧文件流程。
6. 证据与构建：为每个验收项生成绑定候选提交哈希的端到端脚本、数据库清理/断言日志和 pipeline 三门证据。

### 阶段 D：independent test（独立测试节点）

在新会话使用候选提交的干净分离工作树，只读产品源码，独立运行完整 build/test/audit。重点检查：事务回滚无残留、邀请幂等、角色越权、群标识越权、并发接受/移除唯一性、解散后写拒绝、在线事件与界面按需查询、未打开群不提前拉取，以及旧业务回归。测试节点只写证据和交接，不修源码。

### 阶段 E：repair（修复节点）

由需求分支 owner 在新会话消费独立测试发现，逐项修复并重新运行三门。任何验收标准或阈值不得因测试失败而放宽；修复后重新绑定证据哈希。

### 阶段 F：independent audit（独立审计节点）

由不同代理在只读分离工作树审查候选差异、pipeline 报告和 CodeGraph（代码关系图）影响闭包，确认协议冻结路径、权限边界、事务并发和客户端兼容性。审计报告必须明确每个发现的事实依据和处置状态。

### 阶段 G：integration（集成节点）

仅在以下三条事实同时成立时 no-ff（非快进）合入 `master`：独立审计报告已接受、冻结路径差异为空或已完成批准处置、合并结果 pipeline 全绿。任一缺失都停止合并并报告缺口。

## 5. 验收与验证映射

| 需求验收 | 主要验证 |
|---|---|
| 建群失败无残留 | 故意制造第二步失败，断言 `group_info` 与群主成员均无残留 |
| 邀请重复请求幂等 | 相同幂等键并发/重放，断言只有一个逻辑结果；拒绝/过期后按规则可重新邀请 |
| 角色和生命周期权限 | 群主、管理员、普通成员、非成员矩阵；转让、任免、退出、移除、重入、解散全覆盖 |
| 成员列表隔离 | 伪造其他群标识和非成员身份，断言无数据泄露 |
| 并发状态唯一 | 接受与移除对打、多连接重试，断言只有一个有效成员状态且无重复有效行 |
| 旧业务兼容 | 登录、好友、一对一聊天、旧文件流程在新旧客户端/未知群类型输入下回归通过 |

## 6. 影响范围、风险与停止条件

影响范围：`Server/` 数据层、协议入口、权限和在线推送；`Client/` 群 UI 与响应分发；数据库迁移与版本闸门；测试和 `project-docs/evidence/` 证据。两份协议头文件是冻结路径，任何改动都必须留有可审计差异。

主要风险：数据库版本升级与既有 FILE-001 迁移不一致；成员软删除与唯一约束设计冲突；并发锁顺序造成死锁或双重有效状态；在线同步写阻塞；旧客户端误处理新类型；群 UI 扩展误伤旧业务。

停止条件：无法在并发下保持唯一成员状态；无法让旧客户端明确拒绝未知类型；发现当前基线与依赖记录不一致；或任一 LARGE 必需节点缺少可验证证据。满足停止条件时回到 goal 重新评估，不在开发节点临时扩范围。
