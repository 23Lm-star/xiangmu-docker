## 1. 设计目标与边界

本节点固定群生命周期、成员关系、服务端权限、数据库事务、协议兼容和触达语义。实现只覆盖群创建、邀请、接受/拒绝、退出、移除、角色管理、群主转让、解散、群资料/成员/摘要查询，以及成员变化通知。

不实现群消息正文、群文件上传/删除和群公告。GROUP-002/003 必须复用本设计的成员状态和解散状态判定。

## 2. 数据模型

### 2.1 数据库版本

当前 FILE-001 已使用 `schema_version`（数据库版本表）版本 `2026092901`。GROUP-001 迁移目标定为 `2026093001`，通过独立 `Server/migrate_ext_group_001.sql`（迁移脚本）写入版本行；回滚脚本只删除本需求新增表和版本行，不修改既有文件资产数据。

服务端 `OperateDB::checkSchemaVersion()`（数据库版本检查）将要求新版本后再监听端口。迁移脚本必须幂等，可重复执行；低版本数据库继续 fail-fast（启动失败并明确提示），禁止运行时静默建表。

### 2.2 `group_info`（群基本信息）

| 字段 | 语义与约束 |
|---|---|
| `group_id` | `BIGINT UNSIGNED` 自增主键，群唯一标识 |
| `group_name` | `VARCHAR(128)`，非空；服务端校验长度和控制字符 |
| `creator_name` | 创建者账号，非空；仅服务端身份可写入 |
| `status` | `active`（可写）或 `dissolved`（已解散只读） |
| `version` | `BIGINT UNSIGNED`，每次成员/角色/资料变化递增，用于并发审计 |
| `created_at` | 创建时间，数据库生成 |
| `updated_at` | 最近变更时间 |

对 `status`、`creator_name` 建索引。解散采用状态更新，不级联物理删除。

### 2.3 `group_member`（群成员关系）

| 字段 | 语义与约束 |
|---|---|
| `group_id` | 群标识，参与联合唯一键 |
| `user_name` | 用户账号，参与联合唯一键 |
| `role` | `owner`（群主）、`admin`（管理员）或 `member`（普通成员） |
| `status` | `active`（当前成员）、`left`（主动退出）或 `removed`（被移除） |
| `last_read_seq` | `BIGINT UNSIGNED DEFAULT 0`，为 GROUP-002 预留的未读游标 |
| `joined_at` | 首次加入时间，保留历史 |
| `updated_at` | 最近状态/角色变更时间 |

主键使用 `(group_id, user_name)`，保证同一用户在同一群只有一条历史关系；另建 `idx_group_member_user_group(user_name, group_id)` 联合索引，支持按用户获取其所在的全部群聊并覆盖“我的群聊”列表查询。重入只把 `left/removed` 更新为 `active`，不插入第二行；当前有效成员由 `status='active'` 判定。迁移不依赖 MySQL 部分索引，唯一性由联合主键、用户优先联合索引、事务锁和条件更新共同保证。

### 2.4 `group_invitation`（群邀请）

| 字段 | 语义与约束 |
|---|---|
| `invitation_id` | 自增主键，邀请唯一标识 |
| `group_id` | 群标识 |
| `inviter_name` | 邀请人账号 |
| `target_name` | 目标用户账号 |
| `status` | `pending`（待处理）、`accepted`（已接受）、`rejected`（已拒绝）或 `expired`（已过期） |
| `expires_at` | 过期时间；接受前必须重新比较数据库时间 |
| `request_key` | 请求幂等键，非空；同一逻辑重试必须复用 |
| `created_at` / `handled_at` | 创建和处理时间 |

建立 `(group_id, request_key)` 唯一索引。创建邀请时先锁定群和目标成员，再检查该目标的待处理邀请；同群同目标的不同幂等键在已有待处理邀请时返回业务冲突。拒绝或过期后允许使用新幂等键再次邀请，旧邀请记录保留。

## 3. 状态转换与事务

### 3.1 统一锁顺序

所有改变群状态的事务按固定顺序获取锁：

1. `group_info` 按 `group_id` `FOR UPDATE`（行级锁）。
2. 需要时锁定目标 `group_member(group_id,user_name)`；不存在时锁定同群目标邀请查询范围。
3. 需要时锁定 `group_invitation(invitation_id)` 或同群同目标待处理邀请。
4. 完成校验、写入状态和递增 `group_info.version`，最后提交。

固定顺序用于降低接受/移除、邀请/重试之间的死锁风险。任何条件不满足都回滚并返回明确业务结果；不发送事件直到事务提交成功。

### 3.2 核心操作

| 操作 | 事务语义 |
|---|---|
| 创建群 | 插入 `group_info` 与 `owner` 成员必须同一事务；任一步失败整体回滚 |
| 发起邀请 | 校验群为 `active`、操作者为群主/管理员、目标存在且不是当前成员；幂等键重放返回同一逻辑结果 |
| 接受邀请 | 锁群、锁邀请、校验目标身份/过期状态，再将已有历史成员重激活或插入首行；邀请与成员更新同一事务 |
| 拒绝邀请 | 仅待处理邀请可转为 `rejected`；重复请求返回已处理结果，不重复改状态 |
| 主动退出 | 只有当前成员可退出；群主必须先转让或解散，不能留下无群主群 |
| 移除成员 | 群主可移除普通成员；管理员只能移除普通成员；状态改为 `removed`，不物理删除 |
| 任免管理员 | 仅群主可操作；目标必须是当前成员；群主角色不通过普通任免接口改变 |
| 转让群主 | 群主在同一事务内把目标成员改为 `owner`、自己改为 `admin`；目标必须为当前成员 |
| 解散群 | 仅群主可操作；`group_info.status` 改为 `dissolved`，成员/邀请/历史保留；所有后续写操作拒绝 |
| 成员/群摘要查询 | 先校验当前身份具备查看权限，再按群标识查询；不能通过替换群标识读取他群 |

### 3.3 幂等和并发结果

- 同一邀请 `request_key` 的重复请求只返回同一邀请结果，不创建第二行。
- 同一待处理邀请的并发接受只有一个事务能从 `pending` 转换成功；另一个事务看到已处理状态并返回重复处理结果。
- 接受与移除竞争由群锁和成员行锁串行化，最终状态只能是一个确定结果；测试必须记录胜出事务和数据库最终行。
- 事件发送失败只记录失败，不回滚已提交的数据库状态；客户端可通过群摘要/邀请查询补偿。

## 4. 权限模型

服务端从连接级 `actor`（认证主体）取得操作者，不使用客户端载荷中的自报用户作为授权依据。

| 操作 | 群主 | 管理员 | 普通成员 | 非成员/未知群 |
|---|---:|---:|---:|---:|
| 查看群资料/当前成员 | 允许 | 允许 | 允许 | 拒绝 |
| 邀请用户 | 允许 | 允许 | 拒绝 | 拒绝 |
| 接受/拒绝发给自己的邀请 | 按目标身份 | 按目标身份 | 按目标身份 | 拒绝 |
| 主动退出 | 需先转让或解散 | 允许 | 允许 | 拒绝 |
| 移除普通成员 | 允许 | 允许 | 拒绝 | 拒绝 |
| 移除群主/管理员 | 仅转让或群主专用流程 | 拒绝 | 拒绝 | 拒绝 |
| 任免管理员/转让群主 | 允许 | 拒绝 | 拒绝 | 拒绝 |
| 修改资料/解散 | 允许 | 拒绝 | 拒绝 | 拒绝 |
| 已解散群的任何写操作 | 拒绝 | 拒绝 | 拒绝 | 拒绝 |

失败响应不泄露他群是否存在；成员列表和邀请查询使用统一的无权限结果。

### 5.2 载荷编码

不直接发送 C++ 结构体。所有新请求的 `caData`/`caMsg` 使用手工小端编码：

- `uint16 protocol_version`（协议版本）
- `uint16 envelope_length`（公共信封长度）
- `uint64 request_id`（请求唯一标识）
- `uint64 group_id`（群标识；建群请求为 0）
- 业务字段按 `uint32 length + UTF-8 bytes` 编码，整数使用固定宽度。

服务端先验证 `uiMsgLen`（载荷长度）、信封长度、版本和每个字段边界，再进入权限或数据库逻辑。不得读取超出声明长度的数据。已知类型但版本不支持时返回明确的“不支持版本”；未知类型返回对应通用拒绝响应并记录协议版本，不映射到旧业务类型。

## 6. 在线与按需触达

- 成员状态提交后，服务端构造事件并遍历当前群成员；每个在线账号只向当前有效连接发送一次，发送失败记录账号和错误。
- 事件包含群标识、事件版本、变化类型和必要摘要，不包含未授权成员详情。
- 登录过程不主动拉取群邀请、群摘要或群消息。用户进入群聊模块时，客户端才按需查询当前用户的群列表和待处理邀请；查询结果以数据库为准，可以修复事件丢失。
- 用户在群列表中打开某个群聊时，群聊界面才按需请求该群的历史消息和未读摘要；消息正文由 GROUP-002 实现，本需求只固定触发时机和成员鉴权入口。
- 事件发送不参与数据库事务，禁止在网络写失败时回滚成员状态。
- 多连接、慢连接和重复事件的更完整队列化留给后续可靠消息需求；本节点至少保证状态不丢和查询可补偿。

### 6.1 客户端模块布局

主界面在好友和文件模块旁增加独立的群聊模块，保持同级入口，不把群功能塞入好友列表。群聊模块内部至少包含：我的群聊列表、待处理邀请入口、群聊窗口、成员列表和群主/管理员操作区。进入模块或打开具体群聊时再发起对应查询，登录阶段只完成现有认证和旧业务初始化。

## 8. 验证方案

### 8.1 端到端场景

1. 创建群第二步失败：确认群和群主成员均回滚。
2. 相同邀请幂等键并发重放：确认只有一个邀请逻辑结果。
3. 接受邀请重复/过期/拒绝后重邀：确认状态转换和重新邀请规则。
4. 群主、管理员、普通成员、非成员权限矩阵：确认所有越权写入拒绝且不泄露他群信息。
5. 接受与移除并发对打：确认最终只有一个有效成员状态。
6. 退出、重入、转让、解散：确认历史保留、解散后写拒绝。
7. 在线事件失败后重新进入群聊模块：确认邀请和群摘要仍可查询，登录阶段没有额外群查询依赖。
8. 打开具体群聊：确认仅在界面触发后拉取消息和未读摘要，未打开的群不提前拉取。
9. 新旧客户端和旧业务回归：登录、好友、一对一聊天、旧文件流程保持通过。

### 8.2 证据要求

测试脚本绑定候选提交哈希，保存服务端日志、数据库最终状态和协议拒绝结果。development 节点完成后先跑 pipeline 三门；independent test（独立测试）使用干净分离工作树重跑；independent audit（独立审计）只读检查差异、三门报告和 CodeGraph（代码关系图）影响闭包。
