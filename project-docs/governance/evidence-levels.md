# 证据等级定义（Evidence Levels）

> 目的：终结“静态/模拟验证被当作完整动态回归通过”的误称。
> 任何测试报告/缺陷关闭结论**必须**标注所依据的证据等级；等级不足时结论必须降级。

## 等级表
| 等级 | 名称 | 含义 | 能支撑的结论 | 典型手段 |
|------|------|------|--------------|----------|
| L0 | 未验证 | 无独立验证 | 不得声称任何“通过” | — |
| L1 | 静态审查 | 仅代码阅读/静态分析 | “静态实现确认”“代码层面符合” | Bug 查找师审查、编译通过 |
| L2 | 模拟/单元（进程内） | 用 mock/内存库/单进程自测，未接真实服务 | “模拟验证通过”“单元自洽” | SQLite 模拟、tier2 仿真、单元测试 |
| L3 | 集成/系统动态 | 真实 Client+Server+真实 DB/网络端到端 | “动态回归通过” | 真实环境联调、端到端脚本 |
| L4 | 用户验收 | 用户在真实环境确认 | “允许交付/验收通过” | 用户执行反馈 |

## 强制绑定规则
1. 测试报告必须记录：**被测 commit hash** + **evidence_level** + **环境**（真实/模拟）。
2. 缺陷要标“已修复/完整回归通过”，其证据必须 ≥ L3 且被测 commit == 修复 commit。
3. 仅 L1/L2 时，缺陷状态最高只能到“待复查/已确认”，不得写“已修复（动态）”或“完整回归通过”。
4. 结论措辞必须与等级匹配，禁止升级表述（如把“静态实现确认”写成“动态回归通过”）。
