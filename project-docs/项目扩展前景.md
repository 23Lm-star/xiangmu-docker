# 项目演进与扩展需求方案 (v2.0 规划)

> 维护者：项目架构师
> 状态：规划中（已提入架构演进路线图）

基于目前项目的实现基础（基于 QTcpSocket 和自定义 PDU 的 Client-Server 架构、自研三级内存池、单文件顺序 ACK 分块上传、服务端线程池异步写盘、MySQL 连接池支持），规划以下系统扩展需求方案大纲。以下项目均为规划，不应与当前已实现能力混淆。

## 1. 核心业务功能扩展 (Business Features)

当前仅支持 1v1 聊天和基础文件增删改传。扩展方向将围绕“群组协作”与“云盘特性”展开。

| 需求编号 | 扩展功能模块 | 功能说明 | 架构/接口影响与实现思路 |
|----------|--------------|----------|-------------------------|
| **EXP-BUS-01** | **群组聊天 (Group Chat)** | 支持创建群、邀请入群、群组广播、群内成员查看。 | 新增 `group_info` 与 `group_member` 数据表；PDU 需新增 `ENUM_MSG_TYPE_GROUPCHAT_*` 系列枚举；服务端 `MsgHandler` 需支持群发消息的遍历分发机制。 |
| **EXP-BUS-02** | **文件秒传 (Fast Upload)** | 利用文件 MD5 哈希校验，如果服务器已存在相同内容文件，直接建立软链接/数据库映射。 | 客户端在发送 `UPLOADFILE_INIT` 前先发 `UPLOADFILE_CHECK_MD5`。若命中，服务器仅增加一条文件的虚拟记录。需建立全局文件 Hash 索引表。 |
| **EXP-BUS-03** | **公共分享外链 (Public Link)** | 生成带提取码的文件下载外链，类似于百度网盘。 | 服务端生成唯一的短码映射（存于 DB），未来可引申出轻量级的 HTTP Server 模块用于提供外链下载页（与当前的 TCP 二进制协议平行）。 |
| **EXP-BUS-04** | **富媒体消息支持 (Rich Media)** | 支持在聊天中发送图片缩略图、表情包或短语音。 | 消息体不能仅依赖 `char msg[]` 文本，PDU 中的数据载荷区需支持携带富媒体资源 ID 甚至直接分块传输二进制图片（结合现有的文件分块收发协议）。 |
| **EXP-BUS-05** | **引用式文件分享 (Reference Sharing)** | 好友分享和链接领取不再复制物理文件，而是创建带权限的逻辑引用。 | 引入 `file_object`（物理内容）和 `user_file`（用户视图）两层模型；分享只增加引用和授权记录，编辑时采用写时复制。 |

## 2. 系统健壮性与网络层演进 (Reliability & Network)

当前网络模型为裸 TCP，缺乏异常状态处理和优雅的反馈机制。

| 需求编号 | 扩展功能模块 | 功能说明 | 架构/接口影响与实现思路 |
|----------|--------------|----------|-------------------------|
| **EXP-NET-01** | **应用层心跳机制 (Heartbeat)** | 解决假死连接问题，自动释放僵尸客户端资源。 | 引入 `PING/PONG` PDU 类型。客户端每 30 秒发送心跳；服务端 `MyTcpSocket` 记录最后活跃时间，配合定时器踢出超时连接（清理 `tcpsocketlist` 和 DB 的 online 状态）。 |
| **EXP-NET-02** | **断线自动重连** | 网络波动后，客户端自动重新建立 TCP 连接并恢复会话状态，无缝收发缓存的消息。 | 客户端需实现重连退避算法（Exponential Backoff）；重连后发送携带 Token/SessionID 的恢复请求，而非重新输入密码登录。 |
| **EXP-NET-03** | **UI 异步进度与队列控制** | 修复目前文件操作（如大文件下载与复制分享）引起的 UI 阻塞，增加传输速率显示。 | 淘汰现有的单线程阻塞读写，全面转向 Qt 的事件循环异步读写（`readyRead`/`bytesWritten`）；引入上传/下载任务调度队列。 |
| **EXP-NET-04** | **可恢复上传任务与有限并发** | 支持暂停、恢复、取消、多文件队列和失败重试。 | 用持久化 `upload_session` 管理临时文件、会话状态和已确认偏移量；客户端 `UploadTaskManager` 控制最大并发数，每个请求和 ACK 均携带 `sessionId/taskId`。 |
| **EXP-NET-05** | **动态分片与并行大文件上传** | 按网络状态调节分片大小，后续支持单文件多分片并行上传。 | 初始化响应下发 `recommendedChunkSize` 与 `maxInFlightChunks`；乱序分片须改用 `chunkIndex + completedChunks` 位图，不能复用当前单一连续 offset 语义。 |

## 3. 安全防护演进 (Security)

从简单的演示安全机制，转为防窃听、防碰撞的可靠系统。

| 需求编号 | 扩展功能模块 | 功能说明 | 架构/接口影响与实现思路 |
|----------|--------------|----------|-------------------------|
| **EXP-SEC-01** | **传输层加密 (TLS/SSL)** | 防止 PDU 被抓包直接读取账号密码及聊天内容。 | 在现有的 `QTcpSocket` 与 `QTcpServer` 基础上，平滑升级至 `QSslSocket` 与 `QSslServer`。服务端加载自签名证书。 |
| **EXP-SEC-02** | **数据库凭据加密与加盐哈希** | 废弃无盐 MD5 密码存储；剥离硬编码的数据库密码。 | 使用 Bcrypt 或 PBKDF2 对用户密码加盐存储（提升彩虹表破解难度）。配置系统由明文 `connect.config` 转为使用受保护的环境变量或加密的本地配置。 |
| **EXP-SEC-03** | **单账号唯一有效会话** | 同一账号新设备登录后，旧设备立即失效并被通知下线。 | 增加 `session_id/session_version`；新登录在事务内递增版本并主动断开旧连接，所有鉴权请求比对 socket 保存的版本与服务端当前版本。 |

## 4. 上传任务与分片传输专项设计

### 4.1 暂停、恢复、取消

当前上传以单文件、顺序分块和逐块 ACK 为基础。为支持可控中断，需要引入服务端可恢复的上传会话，而非仅在客户端停止发送。

建议新增 `upload_session`：

```text
session_id, user_id, target_path, temp_path, file_size, file_hash,
received_size, status(uploading/paused/canceled/completed/failed), updated_at
```

建议协议字段：

```text
UPLOAD_INIT(sessionId, fileName, fileSize, fileHash)
UPLOAD_PAUSE(sessionId)
UPLOAD_RESUME(sessionId)
UPLOAD_CANCEL(sessionId)
UPLOAD_STATUS(sessionId)
UPLOAD_CHUNK(sessionId, offset, data)
UPLOAD_ACK(sessionId, nextOffset, status)
```

- 暂停：客户端停止投递新分片；服务端将会话设为 `paused`，保留临时文件和已确认位置，并拒绝后续在途分片写入。
- 恢复：客户端查询会话状态后，从服务端返回的 `nextOffset` 继续。网络重连或客户端重启后仍可恢复。
- 取消：服务端先将会话设为 `canceled`，再异步删除临时文件，避免取消后在途分片重新写入。
- 清理：定时回收长期处于 `paused`、`failed`、`canceled` 的会话及临时文件。

多文件上传在客户端通过 `UploadTaskManager` 维护等待、运行、暂停、失败、完成五类任务，并限制最大并发量；同一 TCP 连接复用多个任务时，`sessionId/taskId` 是 ACK 路由的必要字段。

### 4.2 动态分片大小和并行分片

固定 4096B 分片在大文件和高 RTT 网络下 ACK 往返次数过多。初始化响应可返回：

```text
resumeOffset, recommendedChunkSize, maxInFlightChunks
```

分片大小建议在 4KB 到 1MB 范围内受控调整：网络稳定、ACK 延迟低时逐步增大；出现 ACK 超时、写缓冲高水位或重传时立即缩小。服务端必须限定最大 PDU 长度，客户端不能任意声明分片大小。

单文件多分片并行上传是下一阶段能力，与当前严格连续 offset 不兼容。需要改用：

```text
sessionId, chunkIndex, chunkOffset, chunkLength, chunkHash
```

服务端预分配临时文件并保存已完成分片位图；各分片可以按 offset 写入，但必须以 `sessionId + chunkIndex` 做幂等键。全部分片完成后，服务端计算完整 SHA-256，校验通过才原子重命名为正式文件。文件读取、哈希计算可在线程池执行，但 `QTcpSocket` 仍只由其所属网络线程操作。

## 5. 引用式分享与存储模型

当前好友分享和链接领取以物理复制实现，分享给多个用户会产生多份字节数据。引用式分享将“物理内容”与“用户文件视图”分离：

```text
file_object: object_id, content_hash, physical_path, size, ref_count
user_file:   user_file_id, owner_id, object_id, parent_id, display_name,
             permission(owner/editor/viewer), source_user_file_id, deleted_at
```

分享或领取时，只为接收者新增指向同一 `file_object` 的 `user_file` 和权限记录；删除接收者视图仅删除其引用，`ref_count` 归零后异步回收物理对象。普通分享默认只读；接收者编辑时创建新的 `file_object` 并更新自己的 `user_file`，即写时复制，避免修改源文件。

该模型同时为文件秒传、内容去重、版本管理、回收站和分享撤销提供基础。迁移阶段需要先建立文件元数据表，再将已有用户路径逐步导入；不能直接删除既有目录结构。

## 6. 单账号唯一有效会话

`user_info.online` 只能表示“是否有人在线”，无法区分同一账号的多条 TCP 连接，因此不能用于保证唯一登录。建议增加独立会话记录：

```text
user_session: user_id, session_id, session_version, connection_id,
              login_time, last_active_at, status
```

登录成功时，在数据库事务内递增该用户的 `session_version`，并将新值绑定到新 socket。服务端主动向旧 socket 发送“账号已在其他设备登录”通知后关闭它；即使旧连接因网络原因暂未关闭，它发起聊天、文件、心跳等请求时也必须校验：

```text
socket.sessionVersion == currentSessionVersion(userId)
```

不相等则拒绝请求并断开连接。版本校验才是唯一登录的最终保证，主动踢下线只是体验优化。并发登录通过用户行锁或等价事务串行化，后完成登录的会话成为唯一有效会话。

## 7. 架构解耦与现代化 (Architecture Evolution)

为支持将来的高并发需求和更好的可维护性准备。

| 需求编号 | 扩展功能模块 | 功能说明 | 架构/接口影响与实现思路 |
|----------|--------------|----------|-------------------------|
| **EXP-ARC-01** | **消息载荷序列化 (Protobuf/JSON)** | 目前的自定义 PDU 扩展字段极度受限于 `caData[64]`。 | 保留 PDU 包头用于粘包拆包，但将柔性数组区域替换为 Google Protobuf 或 JSON 格式序列化流。这将极大增强接口扩展的灵活性，避免无尽的枚举和数据结构扩充。 |
| **EXP-ARC-02** | **逻辑与存储微服务剥离** | 将文件存储 IO 与高频的聊天路由分离。 | 目前服务端既处理数据库，又读写本地磁盘（还会受限于内存池分配大对象）。架构上可将"文件服务器"剥离为独立进程，客户端鉴权后直接通过 Token 与文件服务器建立连接上传/下载。 |
| **EXP-ARC-03** | **缓存层引入 (Redis)** | 减轻高频查询对 MySQL（及连接池）的压力。 | 用户的在线状态（`online`）、心跳更新、以及 `friend` 关系的快速校验，从 MySQL 迁移到 Redis，提升 QPS 并解决并发锁争用风险。 |

---

### 实施路径 (Roadmap)

建议按以下顺序实施，先解决状态与一致性，再扩展吞吐和存储模型：

1. **EXP-SEC-03 / EXP-NET-04**：会话版本校验和上传会话，补齐唯一登录、暂停、恢复、取消的状态基础。
2. **EXP-NET-05**：动态分片、上传任务队列；并行分片须在会话和幂等逻辑稳定后实施。
3. **EXP-BUS-05**：建立 `file_object/user_file` 元数据层，逐步将复制式分享迁移为引用式分享。
